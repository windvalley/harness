# harness

harness 是一套面向 AI 编程 Agent 的 AI-Native 研发流程与交付门禁。Agent 主导从需求到交付的完整研发过程，通过自动化验证、独立评审和门禁把关质量，你只需参与关键决策和最终验收。

- **按任务规模推进**：小改动核实范围后可以直接实施；大需求先澄清、制定方案，获得你的实施授权后再动手。
- **失败自动闭环**：检查或评审不通过时，Agent 根据问题修复并重新验证、评审；无法自行解决时说明阻塞。
- **两种交付方式**：可以由 Agent 合入本地主分支，也可以提交 PR/MR，由你或团队在平台上合并。

门禁判定在本机完成，不依赖云端 CI。能力边界见[信任模型与已知限制](docs/reference.md#信任模型与已知限制)。

## 快速开始

需要：

- macOS 或 Linux，Node.js 20 及以上，git 2.38 及以上。
- 用于独立代码评审的 AI 工具：推荐本机已登录的 Claude Code CLI（`claude`）或 Codex（`codex`）；其他工具或服务需符合[评审接口要求](docs/reference.md#独立评审的后端)。

### 1. 安装 harness 并接入项目

在 AI 编程客户端里打开待接入的项目，对 Agent 说：

```text
我想给当前项目接入 harness：https://github.com/windvalley/harness
请直接从 GitHub 获取最新版本并安装到本机，不依赖本机已有的 harness 仓库或安装；然后适配并接入当前项目，保留已有有效规则和配置，完成验证、评审与交付。需要我亲自操作时，请给出具体步骤。
```

Agent 会获取并安装所需版本到本机共享目录；每个项目通过仓库内的入口锁定版本，多个项目可以共用同一安装版本。Agent 还会调查已有检查和门禁，在任务分支预览接入改动；是否替换已有 husky 等规则，由你决定。

只有配置为 `gate` 的检查会拦截交付。Agent 会先试跑项目现有检查，并说明哪些生效、哪些失败或尚为占位。首次接入涉及门禁变更，交付前你需要在自己终端执行确认命令，对话中的同意不能代替确认。详见[安装](docs/reference.md#安装)与[首次接入](docs/reference.md#首次接入)。

### 2. 启用客户端实时拦截

按 Agent 提示完成客户端操作：Claude Code 重启会话、Codex 信任钩子，或为 DeepSeek Harness 注册本机插件。具体步骤见[客户端那一侧](docs/reference.md#客户端那一侧)。

完成后让 Agent 运行 `doctor`：`[!!]` 表示需要处理，`[?]` 表示配置已就位，但当前客户端是否真正调用钩子尚未验证，不能算作已生效。

### 3. 完成第一个任务

用平常的话描述需求即可。Agent 会检查现有代码和实际影响范围，再决定采用哪种流程：

- **大需求**：“给系统增加用户登录和权限管理功能，支持管理员创建用户、分配角色，并限制不同角色可以访问的页面和接口。”Agent 先澄清关键问题、交付验收清单和方案，等你明确同意实施后才继续。最初提出需求不算实施授权。
- **小需求**：“在创建用户的表单中增加邮箱格式校验，输入不合法时显示错误提示，并阻止提交。”如果只是现有表单的局部校验，不涉及接口、数据结构或权限变化，Agent 可以直接实施；发现超出小任务范围时转为先讨论、出方案。

实现、验证、评审和交付汇报由 Agent 负责。你只需核对最终效果、验收证据与交付状态；未执行项和阻塞也应明确列出。任务分支和 Worktree 默认保留，需要时可按[清理流程](docs/reference.md#清理任务-worktree)处理。

## 一个需求怎么交付

| 阶段 | Agent 做什么 |
| --- | --- |
| 需求与方案 | 检查现有实现，判断任务范围。大需求先澄清并制定验收清单和方案，等待实施授权；小需求核实范围后可直接开始。 |
| 实施与验证 | 按项目规范先写测试、再实现，运行配置的检查；失败则修复并重新验证，形成可核对的证据。 |
| 独立评审 | 由独立评审进程检查需求符合度和工程质量；存在阻断性问题时修改后重评。 |
| 交付与验收 | 门禁核对最新代码的验证、评审及必要确认，再按选定方式交付；Agent 汇报结果，由你最终验收。 |

任务分级与先红后绿主要由 Agent 执行，harness 只能强制检查其中可机械判定、已配置的部分。例如，大改动在交付时可能因缺少实施授权而被拒绝；配置 `testFirst` 或 `coverage` 后，验证还会检查相应的测试证据。详见[任务分级与实施授权](docs/reference.md#任务分级与实施授权)和[信任模型与已知限制](docs/reference.md#信任模型与已知限制)。

## 三层门禁

| 层 | 生效时机 | 把关内容 |
| --- | --- | --- |
| 实时拦截 | 支持的客户端已启用钩子后，每次工具调用前 | 按规则拦截读取密钥、危险 git 操作和门禁绕过等行为。 |
| git 钩子 | 项目钩子安装并生效后，提交或更新引用时 | 检查提交信息、暂存的敏感文件和本地主分支写入。 |
| 受控交付 | 通过 `harness merge` 或 `harness submit` 交付时 | 核验验证证据、独立评审、实施授权以及必要的人工确认。 |

部分客户端还支持[收尾检查](docs/reference.md#收尾检查)，促使 Agent 在结束回复前核对交付状态，但它不能保证任务一定完成。没有接上实时拦截的客户端不会获得这层保护；经通用入口接入的 Agent 也没有收尾检查。

harness 不代替 GitHub/GitLab 的平台分支保护，也不防拥有本机权限、有意绕过规则的人或进程。具体限制见[信任模型与已知限制](docs/reference.md#信任模型与已知限制)。

## 两种交付方式

| | 本地交付（默认） | 远程交付（PR/MR） |
| --- | --- | --- |
| 谁合并 | Agent 通过 `harness merge` 合入本地主分支 | Agent 通过 `harness submit` 创建或更新 PR/MR，由你或团队在平台上合并 |
| 本地主分支更新 | `harness merge` | 平台合并后通过 `harness sync` 快进 |
| 需要准备 | 本地 git 仓库 | 已安装并登录 `gh`（GitHub）或 `glab`（GitLab） |

区别在于**谁负责最终合并**，而不是仓库有没有托管在 GitHub/GitLab。两种方式由项目的 `.harness/config.json` 选择，不能同时启用。远程交付只保证 harness 提交的 PR/MR 已通过本机门禁；平台最终合入的内容仍由团队的保护规则把关。

首次接入默认使用本地交付。想改为 PR/MR，可对 Agent 说“这个项目改用 PR/MR 交付，平台是 GitHub”；切换交付方式需要你确认。具体步骤见[交付方式：本地与远程](docs/reference.md#交付方式本地与远程)。

## 升级 harness

需要升级当前项目时，对 Agent 说：

```text
请从 GitHub 获取 harness 最新版本：https://github.com/windvalley/harness

安装并升级当前项目，保留已有规则和配置，完成迁移检查、验证、评审与交付。需要我操作时，请提供具体步骤。
```

Agent 会核对版本和升级影响，具体见[升级说明](docs/reference.md#升级)。
