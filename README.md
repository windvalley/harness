# harness

harness 是跑在本机的研发门禁，面向“Agent 写代码、人把关”的 git 项目。
它在 Agent 调用工具时拦下危险操作，在合并前要求验证证据与独立评审，并让主分支只接受它的合并命令写入。
所有判定都在本机完成，不依赖云端 CI，也没有 npm 依赖。

**[阅读图文使用教程](https://windvalley.github.io/harness/)**：架构图、核心原理和上手步骤都在这里。
配置项与命令的完整说明见[参考手册](docs/reference.md)。

## 它管什么

| 层 | 何时生效 | 管什么 | 覆盖谁 |
| --- | --- | --- | --- |
| 实时拦截 | Agent 每次调用工具之前 | 读取密钥、改写门禁入口、不可逆的 git 操作、绕过开关 | Claude Code、Codex、DeepSeek Harness |
| git 钩子 | 每次提交与引用更新 | 提交信息、暂存的密钥文件、主分支的写入 | 所有客户端和人 |
| 受控合并 | 合并到主分支时 | 验证证据、独立评审、门禁改动的人工确认 | 所有客户端和人 |

前两层负责当场纠正，拦截信息里带着原因和正确做法，Agent 照着改道即可。
第三层负责结果把关：即使某个客户端没有接上实时拦截，没有证据和评审的改动也进不了主分支。

## 快速开始

需要：

- macOS 或 Linux，Node.js 20 及以上，git 2.38 及以上。
- 本机已登录的 `claude`（Claude Code CLI）或 `codex`，用来做独立评审；两者都没有时见[独立评审的后端](docs/reference.md#独立评审的后端)。

### 1. 获取 harness

在 AI 编程客户端里打开待接入项目，把下一节的请求交给 Agent。
Agent 会检查运行环境，查找本机已有的 harness，没有时从 [harness 仓库](https://github.com/windvalley/harness)获取。
harness 没有 npm 依赖，也不需要全局安装；手工获取方式见[安装](docs/reference.md#安装)。

### 2. 接入项目

直接对 Agent 说：

```text
我想给当前项目接入 harness：https://github.com/windvalley/harness
```

Agent 应先阅读来源仓库的 README 和接入说明，负责调查、预览和准备工作环境，再写入配置、提交、验证与评审。
任务分支和 Worktree 由它按项目规则准备，首次接入不要求你先手动创建 Worktree，也不一律要求新建一个。
已有 husky、自定义钩子等工具时，Agent 应说明保留或迁移方式；需要舍弃现有规则时先由你决定。

首次接入走受控合并时，Agent 会展示门禁变更摘要，并给出必须由你在终端执行的确认命令。
这一步完成后，告诉 Agent 继续；自然语言同意不能替代这条人工确认。
详细命令见[首次接入](docs/reference.md#首次接入)。

### 3. 让客户端用上实时拦截

按 Agent 给出的提示，完成当前使用的客户端所需的人工操作：重启会话、信任钩子或注册插件。
各客户端的具体步骤见[客户端那一侧](docs/reference.md#客户端那一侧)。

操作完成后告知 Agent 即可，它应接续检查接入状态并说明结果。
你应看到：

- 接入改动已按约定合入，已有有效检查得到保留，项目检查对应真实命令，占位项和未执行项有明确说明。
- Agent 给出诊断结果；`[!!]` 项有处理方案，`[?]` 项说明仍需怎样验证。
- 配置就位与当前客户端实际调用已验证分别说明，未实测的部分不宣称已经生效。

### 4. 完成第一个任务

用平常的话描述想法、问题或希望的变化即可，不需要记住固定提示词，也不必预先写出完整验收标准。
下面两个例子说明不同规模的需求会怎样推进，实际分级由 Agent 核对仓库后判断。

#### 大需求：先讨论，再授权实施

```text
我想让系统支持多个企业使用，企业之间看不到彼此的数据，每个企业还能管理自己的成员和权限。
```

这类需求涉及数据隔离与权限，Agent 应先了解现状，与你讨论关键问题，整理验收标准和方案，然后停下等待你明确同意该方案的实施。
你只需回答问题、判断方案，不需要指挥它结束澄清、写验收清单或生成方案。
最初表达需求不替代方案交付后的实施授权，同意实施也不要求固定措辞。

#### 小需求：核实范围后可以直接实施

```text
列表没有数据时，我希望显示“暂无数据”。
```

Agent 核实这只是已有列表页的局部调整、不涉及接口、数据或权限变化后，可以按小任务规则直接实施。
如果发现实际影响超出小任务范围，应转入先讨论、出方案、再等授权的流程。

理解需求、整理验收标准、澄清关键歧义、准备任务分支和需要的 Worktree、验证、独立评审及交付汇报，都是 Agent 的职责。
你不需要在每次提需求时提醒它提供效果入口、验收结果或合并状态。

完成时检查三个结果：

- 从 Agent 给出的页面或入口查看约定效果；例如小需求中空列表显示“暂无数据”，有数据时列表正常。
- 验收结果对应需求，验证与独立评审有证据，未执行项和阻塞明确列出。
- 最终说明是已合并、待授权合并还是被阻塞，并给出分支、提交和任务工作区位置。

合并后保留任务 Worktree 和分支。
需要清理时再对 Agent 说“请预览可清理的任务工作区”，看过具体对象并确认后由它执行，见[清理任务 Worktree](docs/reference.md#清理任务-worktree)。

## 开发

```bash
npm test
```

自测在临时仓库里运行，使用隔离的数据、密钥与版本目录，不碰本机已有的 harness 安装。
版本号只写在 `package.json` 里。
改了分发的内容（`src`、`assets`、`bin`、`package.json`）就要升版本号：同一个版本号已经装进版本目录、内容又不同时，`publish` 与 `install` 直接报错。
只改 README、CHANGELOG、测试这类不分发的文件，不用升版本号。
发版时更新 `CHANGELOG.md`，打 `v<版本>` 标签并推送：其他机器的 `install --local` 按项目锁定的版本从这个标签安装代码。
标签指向的提交，分发内容要和本机已安装的同版本一致，否则别的机器装出来的门禁和你本机跑的不是同一份。
