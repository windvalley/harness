# harness

harness 是跑在本机的 AI-Native 研发流程，让 Agent 在 git 项目里高质量地完成从需求到交付的全过程。
你和 Agent 聊清需求、同意实施后，Agent 连续完成实现、测试、验证和独立评审，再按项目选定的交付方式把改动送进主分支，中途不需要你逐步安排。
交付方式二选一：默认由 Agent 合入本地主分支；主分支在 GitHub 或 GitLab 上的团队，可以改为由 Agent 提交 PR/MR、在平台上合并，见[两种交付方式](#两种交付方式)。
能否交付由门禁机械判定：没有签名的验证证据、没有通过独立评审的改动，既合不进本地主分支，也提交不了 PR/MR。
没过门禁时，Agent 按拒绝原因修改后重新验证和评审；任务分支放宽不了门禁，删测试、弱化断言也被项目规范禁止。
只有需要你确认门禁改动、同意方案、拍板业务、登录平台，或者同一个问题连续三轮修不好时，Agent 才停下来说明情况；其余时候你只需在交付时验收结果。
所有判定都在本机完成，不依赖云端 CI，也没有 npm 依赖。

**[阅读图文使用教程](https://windvalley.github.io/harness/)**：架构图、核心原理和上手步骤都在这里。
配置项与命令的完整说明见[参考手册](docs/reference.md)。

## 一个需求怎么交付

| 阶段 | Agent 做什么 | 由什么保证 |
| --- | --- | --- |
| 理解与澄清 | 读仓库、判断任务分级；大需求逐个澄清关键问题，写出验收清单、行为说明与实施方案后停下，等你同意实施 | 方案获同意前写不了测试和代码，没有授权记录的大改动合并时被拒 |
| 实施 | 先把每条验收标准写成单元、集成或 E2E 测试并确认失败，再实现到全部通过；只在缺权限、需要业务拍板等情况下停下 | 读取密钥、不可逆的 git 操作等危险调用当场被拦下，Agent 按提示改道继续 |
| 验证 | 在固定检出里按改动路径执行项目配置的检查；未通过时修复后重跑 | 结果写成绑定提交的签名证据，提交一变就要重跑 |
| 独立评审 | 由不了解实现过程的评审进程按验收清单核对需求符合度，并评工程质量；被拒时按发现修改后重新验证、评审 | 需求未满足或有高危发现即拒绝 |
| 交付到主分支 | 本地交付运行 `harness merge` 合入主分支；远程交付运行 `harness submit` 推送核对过的提交并创建或更新 PR/MR，由你或团队在平台上合并 | 两条路都先核对证据与评审对最新提交仍然有效；本地主分支只接受 `harness merge` 与 `harness sync` 写入 |
| 交付 | 逐条给出验收证据、交付状态与待处理项 | 由你最终验收 |

小需求核实范围后跳过方案，直接从实施开始。
任务分级和先红后绿由 Agent 按项目规范执行，门禁兜底其中能机械判定的部分，见[信任模型与已知限制](docs/reference.md#信任模型与已知限制)。

## 三层门禁

| 层 | 何时生效 | 管什么 | 覆盖谁 |
| --- | --- | --- | --- |
| 实时拦截 | Agent 每次调用工具之前 | 读取密钥、改写门禁入口、不可逆的 git 操作、绕过开关 | Claude Code、Codex、DeepSeek Harness |
| git 钩子 | 每次提交与引用更新 | 提交信息、暂存的密钥文件、主分支的写入 | 所有客户端和人 |
| 受控合并 | 交付到主分支时 | 验证证据、独立评审、门禁改动与交付设置变化的人工确认 | 所有客户端和人 |

前两层当场纠正：拦截信息里带着原因和正确做法，Agent 照着改道继续，不需要你介入。
第三层把关结果：即使某个客户端没有接上实时拦截，没有证据和评审的改动也合不进本地主分支，也提交不了 PR/MR。
远程交付下，harness 保证它提交的 PR/MR 通过了本机门禁；平台上最终合入什么，由团队在平台上配置的保护规则把关。

## 两种交付方式

| | 本地交付（默认） | 远程交付（PR/MR） |
| --- | --- | --- |
| 适合 | 主分支在本机，需要时由你推送 | 主分支在 GitHub 或 GitLab 上，合并走 PR/MR 与平台的保护规则 |
| 门禁通过后 | `harness merge` 合入本地主分支 | `harness submit` 推送任务分支，创建或更新 PR/MR |
| 谁来合并 | Agent，在项目授权范围内 | 你或团队在平台上合并，harness 不代为合并 |
| 本地主分支怎么更新 | `harness merge` | 平台合入后用 `harness sync` 快进 |
| 需要准备 | 无 | 本机安装并登录 `gh`（GitHub）或 `glab`（GitLab） |

两种方式只能选一种，由主分支上 `.harness/config.json` 的 `delivery` 决定。
本地交付下 `submit` 会被拒绝，远程交付下 `merge` 会被拒绝；`sync` 只同步远程主分支，两种方式下都能用。

默认是本地交付：`init` 会写入 `"delivery": { "mode": "local" }`，没有这一段的项目也按本地交付处理。
接入时就想用 PR/MR，告诉 Agent 平台是哪个即可，接入分支本身就以 PR/MR 提交。

已经接入的项目要改用 PR/MR，对 Agent 说“这个项目改用 PR/MR 交付，平台是 GitHub”：

1. 你在本机安装并登录 `gh` 或 `glab`；本地主分支有没推送的提交时，先推送到远程，让两边一致。
2. Agent 在任务分支把 `delivery` 改为 `{ "mode": "remote", "provider": "github" }`，验证、评审后给你看确认摘要，摘要里写明 Agent 由此获得的推送任务分支和创建 PR/MR 的权限。
3. 你执行确认命令，Agent 运行 `harness submit` 把这个改动本身作为 PR/MR 提交。
4. 你在平台上合并后，Agent 运行 `harness sync`，此后就改走 PR/MR。

想改回本地交付，按同样的步骤把 `mode` 改回 `local`。
交付方式的任何变化都要你确认，不受其他开关影响，详见[交付方式：本地与远程](docs/reference.md#交付方式本地与远程)。

## 快速开始

需要：

- macOS 或 Linux，Node.js 20 及以上，git 2.38 及以上。
- 本机已登录的 `claude`（Claude Code CLI）或 `codex`，用来做独立评审；两者都没有时见[独立评审的后端](docs/reference.md#独立评审的后端)。

harness 没有 npm 依赖，也不需要全局安装，由 Agent 在接入时获取；手工获取见[安装](docs/reference.md#安装)。

### 1. 接入项目

在 AI 编程客户端里打开待接入的项目，对 Agent 说：

```text
我想给当前项目接入 harness：https://github.com/windvalley/harness
```

Agent 应先阅读本 README 与[参考手册](docs/reference.md)，检查运行环境，查找本机已有的 harness，没有时从上面的仓库获取。
接着调查项目规则、Git 状态、已有钩子和检查命令，预览改动，按项目规则准备任务分支和需要的 Worktree，再写入配置、提交、验证与评审。
已有 husky、自定义钩子等工具时，Agent 应说明保留或迁移方式；需要舍弃现有规则时先由你决定。

接入时 Agent 应和你确定交付方式，默认是本地交付；主分支在 GitHub 或 GitLab 上、合并走 PR/MR 时，见[两种交付方式](#两种交付方式)。

首次接入交付前，Agent 会展示门禁变更摘要，并给出必须由你在自己终端执行的确认命令；对话里的同意不能代替它。
执行后告诉 Agent 继续：本地交付由它合入本地主分支；远程交付由它提交 PR/MR，你在平台上合并后再由它同步。
详细命令见[首次接入](docs/reference.md#首次接入)。
接入完成后 Agent 应说明已有检查是否保留、项目检查是否对应真实命令，以及哪些仍是占位或未执行。

### 2. 让客户端用上实时拦截

按 Agent 的提示完成当前客户端需要的人工操作：重启会话、信任钩子，或为 DeepSeek Harness 注册插件（每台机器一次，所有项目共用）。
具体步骤见[客户端那一侧](docs/reference.md#客户端那一侧)。

完成后告诉 Agent，它会运行 `doctor` 并说明结果：`[!!]` 表示需要处理，`[?]` 表示配置已就位但客户端是否真正调用还没验证，不能算作已生效。

### 3. 完成第一个任务

用平常的话描述想法或问题即可，实际分级由 Agent 核对仓库后判断：

- 大需求，例如“让系统支持多个企业使用，企业之间看不到彼此的数据，每个企业管理自己的成员和权限”：Agent 先了解现状、与你讨论关键问题，交出验收标准和方案后停下，等你明确同意实施，最初提出需求不算同意。
- 小需求，例如“列表没有数据时显示‘暂无数据’”：Agent 核实不涉及接口、数据或权限后直接实施，影响超出预期时转为先讨论、出方案。

澄清、整理验收标准、准备工作区、验证、独立评审和交付汇报都由 Agent 负责，细节见[如何表达需求与后续协作](docs/reference.md#如何表达需求与后续协作)。

完成时检查三个结果：

- 从 Agent 给出的页面或入口查看约定效果。
- 验收结果对应需求，验证与独立评审有证据，未执行项和阻塞明确列出。
- 最终状态明确，并给出分支、提交和任务工作区位置：本地交付是已合并、待授权合并或被阻塞；远程交付是已提交 PR/MR 等平台合并、平台已合入并已同步或被阻塞。

交付后任务 Worktree 和分支会保留，需要清理时让 Agent 先预览，你确认后再执行，见[清理任务 Worktree](docs/reference.md#清理任务-worktree)。

## 开发

```bash
npm test
```

自测在临时仓库里运行，使用隔离的数据、密钥与版本目录，不碰本机已有的 harness 安装。
版本号只写在 `package.json` 里。
改了分发的内容（`src`、`assets`、`bin`、`package.json`）就要升版本号：同一个版本号已经装进版本目录、内容又不同时，`publish` 与 `install` 直接报错。
只改 README、CHANGELOG、测试这类不分发的文件，不用升版本号。
发版时更新 `CHANGELOG.md`，打 `v<版本>` 标签并推送：其他机器的 `install --local` 按项目锁定的版本从这个标签安装代码。
标签指向的提交，分发内容要和本机已安装的同版本一致，否则别的机器装出来的门禁和你本机跑的不是同一份。
