# 需求与工程双维评审

评审、接收反馈或交付前自审时使用；通用约束见 [core](core.md)，不把开发重构移到评审阶段。

- 明确需求、比较基线和所评版本。工作区评审覆盖暂存、未暂存及相关未跟踪文件，不能漏掉未提交改动。
- 分别核对需求符合度与工程质量；没有可核实需求时，需求符合度标未验证，工程检查可继续。问题给出位置、依据和影响，区分硬性缺陷与设计建议。
- 自审不冒充独立评审。harness 的独立评审由没有实现上下文的进程执行，本地自审不替代它。
- 收到评审意见先核对版本、需求与代码，过期或不适用建议要说明依据；涉及未决产品语义时只暂停依赖项。
- 修复后重新验证受影响项，证据对应最终代码状态；保留未解决项，不把建议当成已完成修复。

## 提交后自审

交付前自审放在提交之后、`harness verify` 之前，发现问题先改完并提交，再去验证。
只查独立评审看不到、或者后期才发现很费事的几项，不重复测试已经证明的事：

- 合并前验收清单每条都对应到测试、命令输出或已登记的外部证据，没有漏掉的；合并后条目有对应的 post-merge 检查与补验方式。
- 提交说明如实写出改了什么。
  格式与语言由 `commit-msg` 钩子按 `.harness/policy.json` 的 `commit-message` 规则把关，提交时不合规就会被拒。
  说法与 diff 不符时评审会报发现。
- `git status` 洁净，没有漏提交的文件；diff 里没有无关改动、调试残留与临时文件。
- diff 之外的调用方、配置、文档和测试夹具已经一起改。
  独立评审看到的代码只有 diff 与少量上下文，看不到这些。

自审结论不交给独立评审，也不写进提交说明：评审要独立判断，写进去只会带偏它。
改动很小时，对照这份清单通读一遍 diff 就够了。
