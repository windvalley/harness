# UI 视觉验收

修改页面、组件、交互状态或响应式布局时使用；存在设计资料或对标产品时必须核对其内容。
行为测试遵循 [测试设计](method-test-design.md) 与 core 的先红后绿规则，本方法补充视觉与可访问性证据，不新增审批或门禁类型。

## 实施前确定目标

- 读取可用的设计文档、截图、原型和组件规范，记录来源、版本、页面及状态；用户明确要求优先，不从当前实现反推目标。
- 制作多个原型或比较布局方案前，先建立真实基线：已有页面记录完整应用外壳、目标容器和关键视口下的实测可用宽度，不只画孤立面板；全新页面可以使用已确认的布局约束与明确标注的 fixture，不虚构既有页面结构。
- 原型字段逐项映射真实类型、接口或 fixture；没有数据来源的字段删除或明确标为示意，不伪造真实感内容。小任务把这几项写进验收清单即可，不强制另建视觉文档。
- 没有设计资料时，根据用户目标、项目风格、已有组件与可用性要求确定本次视觉目标并记录依据。
  普通布局、间距、颜色和响应式取舍由 Agent 判断，不要求用户逐项确认。
- 用 [UI 视觉契约](../templates/visual-contract.md) 核对结构、内容、可访问性、交互状态、几何、颜色圆角和响应式要求。
  小任务可把适用字段写进验收清单；复杂或跨会话任务再建立独立文档，不重复维护同一事实。
- 覆盖加载、空状态、错误、恢复和关键视口。
  需要量化时在实施前制定容差或截图阈值及依据，不设置通用像素阈值，也不为通过验收事后放宽既定标准。

## 验证与证据

- 可自动验证的目标先写成 UI 验收测试并确认有效红灯，再实现到通过。
  优先按可访问角色、名称和可见文本定位，不依赖脆弱 DOM 层级；结构、可访问性、可操作性、内容溢出及关键断点错误均为硬失败。
- CSS 断点、网格列数、颜色和尺寸用最终生效的计算样式或真实浏览器行为验证，源码字符串断言只作辅助。
  提交钩子或格式化工具会改写样式时，对改写后的文件复核媒体查询顺序、选择器特异性与目标视口；至少选择一条可观察行为做变异验证。
- 功能 E2E 通过不等于视觉对齐，功能与视觉结论分别记录。
  自动化检查与评分不等于真实可用性；按场景实际验证键盘顺序、焦点、错误提示和辅助技术语义，不能只跑工具评分。
- 截图应对应实施前确定的目标、提交、平台与视口，只保存当前截图不能证明通过。
  缺少历史基线时按既定目标建立本次证据，不自行把现状当成目标。
- 保存结构化结果、关键状态截图及必要的哈希或报告链接，证据不含秘密。
  未在目标平台、视口或真实交互中检查的项标为 `not_evaluated`，说明原因、影响与补验方式。
- 不默认增加人工看图或审批；项目明确要求人工验收或存在真实访问限制时，才列为人工待审。
  外部报告通过 `attest` 登记，合并后义务沿用现有 `post-merge` 流程。
