# 需求澄清与领域语言

需求有歧义、关键取舍未定，或任务需要先方案后实施时使用；通用约束见 [core](core.md)。

- 先查已有需求、契约和代码，并从可用资料、工具和相关入口补齐上下文，仓库和可用资料里能查到的不问用户。
- 上下文足够时由 Agent 判断有明确契约支撑的技术实现、兼容性和失败处理取舍，记录依据后继续，不要求用户替 Agent 设计实现。
- 只有查证后仍无法自行获得且影响结果的关键信息缺失时才询问；一次只问一个问题，等用户答完再问下一个，每个问题给出推荐答案和理由。
- 先问答错会返工且无法查证的问题：产品语义、权限边界、数据与验收；不影响实现或已有明确答案的细节不问，已确认的决定不重复问。
- 产品语义、权限边界和用户可见承诺不能从当前实现反推；没有明确契约时必须由用户确认。
- 主动判断不扩大实施授权、危险操作、门禁改动或外部副作用的授权，原有确认与审批不变。
- 用户说“待定”的问题记下来，接着问下一个；写方案时原样列进待确认，不替用户补上答案。
- 关键问题已明确、已有契约足以判断或由用户标为待定后，主动总结已确认内容与未决问题，进入方案，不要求用户说出结束澄清或开始写方案的指令。
  没有需要澄清的问题时，说明依据后直接进入方案；用户明确希望继续讨论时按其节奏推进。
- 不要求用户预先填写完整验收标准，由 Agent 结合仓库和对话整理，只就无法查证且影响业务含义的歧义向用户确认。
- 澄清答案和对方案细节的认可不等于实施授权，先方案后实施的任务仍须在方案交付后等待用户明确同意实施。
- 沿用项目领域术语，用反例检查同名异义；当前实现不能代替预期行为。
  术语与契约冲突时按用户目标和明确约束处理，需要长期保留的冲突结论在确认后更新原有真源。
- 推断和假设必须标明，不写成用户已确认的事实，也不借推断覆盖明确要求。
- 需要长期保留的术语和重要取舍写入项目已有文档；结论写回已有需求或方案，保留验收、判断依据与剩余问题。
