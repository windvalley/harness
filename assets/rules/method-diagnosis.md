# 故障诊断

缺陷、偶现失败或性能退化时使用；修复与验证遵循 [core](core.md)。

- 从实际日志、输入、版本和环境确认原始症状，建立触达故障路径的最小复现。无法复现时报告缺失条件，继续可独立调查的部分，不凭猜测改生产实现。
- 根因不明时用可证伪假设区分原因，每次只改一个变量；因果已直接证实时不凑步骤。缩小复现不能删掉触发故障所需的参与者。
- 性能问题先建立同环境、同负载的基线；偶现问题记录样本量和失败次数，不用一次成功证明修复。
- 复现转为行为测试后按测试先行流程修复，最后回验原始场景；清理临时插桩，区分已证实原因与猜测。
- 连续修复失败或不断引出新问题时，停止叠加补丁，复核假设、环境与契约，取得新证据再继续；不自行扩大为架构重写。

## 验证入口受阻时

入口失败只证明这条命令没有提供所需证据，不能直接推出目标验收失败或真实行为无法验证。
先阅读检查结果的 `outcome`、`reasonCode`、日志和最终执行计划；`not_run` 还要查看 `blockedBy`，不要把连带未执行项误报为各自失败。

按下面顺序做最小诊断，每一步只取得足以决定下一步的证据：

1. 对照验收清单与项目规则，明确本次必须证明的行为、已取得的证据和仍缺的证据。
   区分必需 `gate`、可选的合并前 `extended` 与合并后义务，不能把可选检查自动变成硬门禁。
2. 判断失败发生在命令启动、依赖准备、台账或配置检查，还是已经进入目标行为。
   `missing_command`、`spawn_error`、`timeout`、`signal`、`missing_dependency` 与 `invalid_config` 按已知事实处理；`command_failed` 只表示普通非零退出，`check_failed` 表示 Harness 内建 TDD 或 coverage 条件未满足，二者都须按具体证据处理。
3. 声称问题在基线已存在时，用已有失败报告、同条件的定向基线复现或可比日志证明，并写明与当前任务的关系。
   不因报错文件未修改就认定存量，也不为证明无关问题默认跑全量基线。
4. 核对是否有项目允许、覆盖同一验收行为的定向测试、真实 DOM 夹具或隔离环境入口。
   例如全局 UI 台账在启动浏览器前失败时，可用真实页面的定向浏览器测试验证受影响交互；只加载页面、只跑静态检查或单元测试，不能代替未覆盖的交互证据。
   夹具应保留被测实现，只在契约边界控制数据；真实后端权限、持久化与外部系统能力仍按风险实测。
5. 在现有授权内可恢复时，完成最小修复或等价验证并记录证据与局限。
   必需 `gate` 仍须通过；定向外部证据不能让失败的 `gate` 自动通过，改变门禁配置仍按人工确认流程处理。
6. 必要验收仍不可行且需要人决定时，再上报具体阻塞、已尝试路径、缺失证据与可选方案。
   已有技术阻塞消除时用 `escalate resolve` 保留解除证据，不把它写成用户 `answer`，也不擅自扩大为无关修复。

沿用 `core.md` 的停止条件，缺权限或需要业务拍板时及时交给人，同一个问题连续三轮没有解决时停止叠加尝试。
诊断本身不要求穷尽所有入口，不要求重复已通过检查，也不新增自动基线修复或检查豁免。
