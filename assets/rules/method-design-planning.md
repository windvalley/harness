# 设计与任务拆分

任务需要先方案后实施时使用，分级见 [core](core.md)。

方案由四份文件组成，放在任务分支里一起提交：

| 文件 | 内容 |
| --- | --- |
| `.harness/acceptance/<分支名>.md` | 验收清单：应该发生什么、绝对不能发生什么、失败时怎么办，每条都能判定对错；独立评审按它逐条核对 |
| `docs/changes/<change-id>/spec.md` | 行为说明：用户卡在哪、目标行为、失败时怎么办、这次不做什么、待确认 |
| `docs/changes/<change-id>/contract.md` | 核心授权契约：用户目标与交付结果、用户可见交互、验收底线、必需证据和权限边界；必写且只有一份，实施授权只绑定它 |
| `docs/changes/<change-id>/plan.md` | 实施方案：验收到测试的对应、实现顺序、交付前的检查、环境与依赖、复用的已有能力；日常更新不影响授权 |

- 分支名里字母、数字、`.`、`_`、`-` 以外的字符换成 `-`；已有对应文档直接复用。
- 项目约定了别的方案目录时沿用，并同时修改 `.harness/config.json` 的 `intent.plan.markers` 与 `plan-before-code` 规则的放行路径。
- 验收清单写清交付结果、兼容性和权限边界，作为后续验收依据。
  核心契约只写事后纠正代价高的承诺；内部技术方案写进实施方案，不写进契约，实现中调整技术方案就不会触发人工确认。
  授权后在契约范围内持续修订验收清单、行为说明和实施方案，分界见 `core.md`；只有核心契约变化才需要由人针对新 hash 重新确认。
  授权时没有 contract.md 的旧记录仍按整份验收清单绑定，不自动迁移授权语义。
- 实施方案记录可自行调整的步骤、已知备选路径及采用条件，也用于记录执行进度和证据。
  授权后改了验收清单、行为说明或实施步骤时，在“授权后修订”章节记一行：改动、类型（细化 / 加严 / 新增 / 删除 / 放宽 / 实现调整）、理由、证据；执行进度的更新不用记。
  harness 以授权时提交为基线机械列出修订条目，这一章节提供理由，评审据此判断修订有没有越过契约。
  重要技术取舍需要额外签名留痕时运行 `harness amend --branch <任务分支> --reason "<原因>"`，它不能代替核心契约的重新确认。
- 交出方案前，按预期改动核对适用的测试入口、`requires` 依赖、运行环境和评审者，优先用 `harness doctor` 查看配置与本机可用性。
  已配置远程交付且允许读取目标仓库时，用 `harness doctor --check-remote` 提前核对平台查询是否可用。
  在方案中说明已发现的阻塞、需由人完成的步骤和预计触发的门禁确认。
- 方案提交后、交给用户之前，本机配置了评审者时运行一轮 `harness review-plan --branch <任务分支>`，让另一个模型审方案，见 `harness.md` 的“方案评审”。
  它只给建议，不是门禁；没配置评审者或评审失败时跳过，并在交付方案时说明。
- 逐条判断评审意见的采纳与否，在 `spec.md` 末尾的“方案评审意见与处理”一节记录：采纳的写改了什么，不采纳的写理由。
  采纳了 high 及以上的意见并实质修改方案后，才跑第二轮，最多两轮。
  采纳意见时，方案修改和这份记录放在同一次提交；没有采纳任何意见时，只提交记录。
  不 amend 已评审过的提交，账本里的 `plan.review` 事件记着被评审的提交。
- 交出方案后停下等用户表态；用户表达开始实施的意思后，连续执行到完成。
  项目启用了 `plan-first` 预设时，先照录用户原话记录授权，见 `harness.md`。
- 用[验收清单](../templates/acceptance.md)、[核心授权契约](../templates/contract.md)、[行为说明](../templates/spec.md)与[实施方案](../templates/plan.md)模板，删掉不适用的章节。
- 实施方案的第一步把每条验收标准对应到测试，标明单元、集成还是 E2E；后面的步骤写清实现顺序、每步的验证方式和什么时候算完成。
- 在已批准的验收和权限内调整实现时，在方案里记录依据，每完成一步标出完成和验证方式。
- 以调用者负担和已有架构约束判断接口；不为想象中的扩展引入抽象，不把设计建议变成未经授权的重构。
- 按可验收行为纵向拆分，注明验收、真实阻塞关系和验证入口。
- 预计一个任务分支交付不完的需求按阶段拆分，每个阶段一份验收清单，并写阶段文件列出阶段顺序、建议分支名与清单路径，见 `harness.md` 的“多阶段方案”。
  交出方案时只通过自然语言询问是否一次授权哪些已确定的阶段，不向用户展示需要亲自执行的 `approve` 命令；得到对话授权后由 Agent 按实际同意范围执行 `approve --stages` 或普通授权。后续阶段使用 `approve --from-stages` 继承授权。
- 跨模块迁移按兼容新增、分批迁移、删除旧实现推进；每批保持必要验证通过，共同集成前不宣称整体可交付。
- 本方法不自动授权多 Agent 委派。已授权并行时明确责任与隔离边界，合并后仍须验证整体行为。
