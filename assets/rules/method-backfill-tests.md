# 遗留补测

用户要求为既有仓库系统补齐缺失测试时使用；修复一个已知缺陷仍按 [故障诊断](method-diagnosis.md) 和测试先行流程处理。
补测只改变测试、夹具与明确需要的测试基础设施，不修改生产代码。
先读 [测试设计](method-test-design.md)，用 [补测盘点](../templates/test-backfill.md) 维护唯一清单，不另建重复进度表。

## 盘点与计划

- 先完成完整的只读盘点，再写测试。
  覆盖 Git 可见的生产文件、测试、测试配置和项目命令，并从用户可观察行为盘点 API、页面、CLI、后台任务及跨组件流程，不能用抽样或目录级概括代替。
- 记录 HEAD、脏路径、已有测试、各层 runner、精确命令和基线结果。
  不选择已有未提交修改的路径；扫描范围受限时明确标为不完整，不能声称已经覆盖整个项目。
- 按实际行为边界选择单元、集成与 E2E。
  可测试功能必须有具体单元用例；组件协作、接口或数据边界使用集成测试，完整用户流程使用 E2E。
  不适用层说明场景依据；缺 runner、环境或账号不等于不适用，可以补测试基础设施时先补基础设施。
- 每个缺口写清目标行为、测试文件、用例、独立期望值、断言和执行命令。
  已有覆盖必须指向真实测试；源码文本匹配、空用例和覆盖率数字不能代替行为断言。
- 按安全与权限风险、不可逆写入、核心链路、外部边界、历史失败、变更频率和复杂度排序，覆盖率只作辅助证据。
  先统一列出全部候选，再按行为数量、执行时间和环境风险分批；批次预算不能把后续候选从清单中删掉。

## 阻断与执行

- 缺 runner、fixture、本地服务或测试配置时，把可自恢复的测试基础设施排在依赖它的用例之前，不为已有仓库能够推导的内容向用户索要答案。
- 既有失败只阻塞相关候选，先以基线、已有报告或可比日志确认失败身份，再运行更窄的合法命令；独立候选继续执行，不因全仓基线失败停止整个补测任务。
- 缺少无法自行获取的业务上下文、测试账号、权限或可复位数据时，只暂停依赖它的候选，其余候选继续。
  不要求用户在聊天中粘贴秘密。
- 只能使用生产凭据、生产写入或不可逆操作的候选保持阻塞，不为提高覆盖率绕过安全边界。
- 每批只写计划中的测试、夹具与测试基础设施。
  发现必须修改生产代码的问题时，把相关候选隔离出来，按原任务授权另走缺陷修复流程，修复后重新盘点，不在补测批次里顺手改实现。
- 逐条运行目标用例和受影响回归，记录通过、失败、阻塞与未评估。
  已有失败不得改写为通过；单批失败不取消仍可独立执行的后续候选。
- 计划完成或命令退出 0 不等于覆盖完整。
  交付前复核每个生产功能与具体用例的对应关系、适用层及断言质量，再按项目流程提交、验证、独立评审和交付。
