# 授权后自主修订方案与验收清单

## 应该发生

- 首次记录实施授权时，任务分支的方案目录里没有 `contract.md`，`harness approve --branch <分支>` 预览标明缺少核心契约，`approve --yes` 以非零退出拒绝并提示按 `.harness/templates/contract.md` 补写；不写授权记录，也不追加账本。
- 首次记录多阶段方案级授权（`--stages`）时，阶段文件里任一阶段没有 `contract` 字段，同样拒绝并点名缺契约的阶段。
- 有核心契约的已授权任务，在授权后新增、删除或改写验收清单、`spec.md`、`plan.md` 的条目时，`status`、`verify`、`merge`、`submit`、写入门禁与收尾检查都认定授权仍然有效，不要求人确认，也不要求 Agent 重新记录授权。
- 核心契约在授权后变化时，现有行为不变：授权失效，需由人执行 `approve --confirm-contract <新hash>` 重新确认，Agent 执行该命令仍被 `contract-reapproval-human-only` 拦截。
- 授权记录里没有核心契约的既有授权（下称旧记录）保持整份验收清单绑定，清单变化后仍失效，重新确认流程与现在一致。
- harness 以授权记录中的授权时提交为基线，机械生成授权后修订摘要：
  - 验收清单与 `spec.md` 按章节列出删除和新增条目的原文；
  - `plan.md` 列出发生变化的章节及增删行数；
  - 原样附上 `plan.md` 的“授权后修订”章节，作为 Agent 写的修订理由；
  - 没有任何修订时写明“授权后没有修订”。
- `status --branch` 显示修订计数一行，`status --handoff` 与 `harness merge` 成功输出显示完整修订摘要，`harness submit` 生成的 PR/MR 描述包含完整修订摘要。
- 独立评审在已授权且有核心契约时，提示中附核心契约原文、验收清单授权版到当前版的修订条目与“授权后修订”章节；清单来源标签写明授权后有修订。
- 评审说明要求：修订与核心契约冲突，或删除、放宽了授权版条目却没有在“授权后修订”章节写明理由时，需求符合度评为 `partial` 并点名条目；来源为已授权时 `partial` 照现有规则拒绝。
- 规则 `core.md`、`harness.md`、`method-design-planning.md` 写明同一条分界：
  - 细化、加严、新增条目，等价或更强的验证方式，调整实现路径与技术方案，修正方案中的事实错误，可以自主修订，交付时汇报；
  - 改变用户目标或交付结果、删除或放宽验收底线、删除必需证据、扩大权限（新增依赖、外部写入、库表或数据迁移、破坏对外兼容、不可逆操作）必须改核心契约，由人重新确认，只暂停依赖它的部分。
- `harness.md` 中“授权绑定验收清单的内容，改清单先取得同意”的表述改为只适用于旧记录，不再与 `method-design-planning.md` 冲突。
- 核心契约模板不再要求填写内部技术方案，只保留用户确认的交付结果与用户可见交互、验收底线、必需证据和授权范围；实施方案模板新增“授权后修订”章节，每条写改动、类型、理由与证据。
- 交付汇报规则要求原样附上 harness 输出的修订摘要。
- 托管块新增一句：已授权任务在核心契约范围内修订验收清单与方案时不停下确认，交付汇报附修订摘要。
- 文档站正文与 `docs/reference.md` 同步新行为，`npm run docs:build` 生成结果与源文件一致。

## 绝对不能发生

- 新任务在没有核心契约的情况下取得实施授权。
- Agent 自行完成核心契约变化后的重新确认。
- 旧记录的授权语义被改变：清单修改后不再失效，或者未修改时被误判失效。
- 修订摘要遗漏实际变化的验收清单条目，或在无法还原基线时报告“授权后没有修订”。
- 修订摘要、评审提示或 PR/MR 描述带出凭据原文。
- 新增第三方依赖或新的 CLI 子命令。

## 失败时

- 授权时提交已被清理、无法还原基线时，摘要写明“无法还原授权时的版本”并给出记录里的提交 hash；授权判定、合并与提交不因此失败。
- 摘要生成过程出错时输出原因，授权判定与合并结果保持不变。
- `approve --yes` 因缺少核心契约被拒绝时，已有授权记录与账本保持原状。
