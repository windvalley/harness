如何表达需求与后续协作

下面是两个普通需求示例，不是必须照抄的提示词模板。用户不需要预先填齐验收标准、安排工作流程或重复交付要求，实际分级由 Agent 核对仓库后判断。

大需求：先讨论，再授权实施

描述想法即可
给系统增加用户登录和权限管理功能，支持管理员创建用户、分配角色，并限制不同角色可以访问的页面和接口。

这类需求涉及认证与授权。Agent 应先了解现状，再与你讨论登录方式、角色权限和现有用户数据兼容等关键问题，主动整理验收清单、行为说明与实施方案。

关键问题已明确或由你标为待定后，Agent 应保留未决问题并说明影响，主动进入方案，不需要你宣布问题问完或指挥写文档。方案交付后它应停下，等待你明确同意实施该方案。

最初表达需求不替代方案交付后的实施授权，对某个澄清答案或方案细节的认可也不等于同意实施。授权不要求固定措辞。

小需求：核实范围后可以直接实施

描述希望的变化即可
在创建用户的表单中增加邮箱格式校验，输入不合法时显示错误提示，并阻止提交。

Agent 核实这只是现有表单的局部校验，不需要调整接口、数据结构或权限且满足小任务条件后，先写一份简短验收清单再直接实施，并验证合法与不合法邮箱的提交行为。小任务不需要另写 spec/plan 或等待方案授权；发现影响超出小任务范围时，应转入讨论、方案和授权流程。

用户当前只要求分析、评估或讨论时仍保持只读，不能因为需求看起来小就动手。用户也可以补充约束或调整节奏。

分支命名

首次接入先调查项目已有明确的分支命名规范，有则优先转换到 .harness/policy.json 的 branch-name 规则，在首次提交接入改动前完成对齐；没有明确约定时才使用 init 生成的默认规则。对齐时保留其他 presets、提交规范和项目规则，已有 policy 不自动覆盖。

运行时只按 policy 判定，Agent 和门禁读取同一份要求，项目原有规范说明及出处继续保留并与 policy 保持一致。默认规则采用 <type>/<task>，允许 feature、fix、docs、refactor、test、chore 前缀，任务描述使用小写英文和数字，单词以 - 分隔。

feature/add-policy-check
fix/123-login-timeout
docs/update-install-guide

默认规则允许数字工单号，拒绝客户端名称前缀、大小写混用和下划线。需要 release/、hotfix/ 或其他格式时，修改项目 policy 中的 pattern 并同步原规范说明；关闭规则沿用 disabled。

客户端启用实时钩子后，git worktree add -b、git switch -c 和 git checkout -b 在仓库和新分支名可以静态确定时，会在执行前检查。已有分支的挂载、分离检出和无法静态确定的建分支命令不由这层拒绝。

pre-commit 仍在提交时拒绝不合规名称，merge、submit 在交付前做最终检查，status 只读展示，doctor 检查配置。手工提交同样受钩子检查，绕过钩子或提交后改名仍会在交付前被拒绝。

verify、review 面向提交内容，不因分支名称不合规而拒绝，规则配置错误仍会提前报出。只改分支名时核对验收清单路径和 status，内容证据与评审仍有效时直接复用。

门禁先解析实际分支名称，支持 HEAD、完整分支引用和远程跟踪分支；配置主分支豁免任务命名要求，原主分支保护保持生效。SHA、tag 和 detached HEAD 可做纯内容验证与评审，但不代表命名通过，启用规则后的交付必须有明确分支来源，detached HEAD 提交会被拒绝。

实际判定取主分支 policy，任务分支不能通过修改自己的配置放行。项目命名要求直接维护在 policy，规则变更经人工确认合入后生效；upgrade 更新指引并保留项目 policy。字段错误、无效正则或重复规则会在进入主分支前被拒绝，详见分支命名参考。

并行任务与 Worktree

新项目的 init 默认启用 main-worktree：主 Worktree 停在主分支，只用于合并、同步与固定环境。每个任务使用独立分支和 Linked Worktree，Agent 在各自目录里修改、提交、验证和评审，不在主 Worktree 里切换任务分支。

merge 和 sync 要求主 Worktree 没有已跟踪文件的未提交改动，也没有进行中的 Git 操作。未跟踪或忽略的本机文件只在与本次检出冲突时阻塞，其他文件原样保留。

两个任务分别从最新主分支建独立目录
git worktree add -b feature/login ../project-login main
git worktree add -b fix/payment ../project-payment main

并行开发不只是目录隔离。依赖安装、端口、数据库、环境变量和测试数据仍需按项目隔离，避免不同任务共用会互相修改的运行资源。机制与多机协作说明见团队与多机。

其他任务先合入主分支后，后续任务按需在自己的 Worktree 吸收最新主分支；出现冲突或 review_stale 时重新验证和评审。每次合并仍由门禁核对最新代码与证据。

worktree.autoClean 默认关闭。清理前活跃任务可用 git -C <主 Worktree> worktree lock <任务目录> 保留，用完再解锁；含本机文件或进程不可知的目录在自动模式下同样保留。

已有项目升级时不会自动开启 main-worktree。需要关闭时从 policy.json 的 presets 删除它；只需允许人工在主 Worktree 提交时，可在 disabled 里只关闭 main-worktree-commit。配置改动仍按门禁流程确认。

一次任务

两类任务都由 Agent 整理验收标准，并先查证仓库、已有契约和可用资料。 大需求在交方案前核对测试依赖、评审者和适用的远程访问，并说明已知的人工环节。 获得实施授权后，Agent 在既定验收和权限范围内自行调整实现、验证、评审并交付。 确需改变验收、业务承诺或权限时，只暂停依赖该决定的部分。 遇到临时平台故障，Agent 按提交状态接续。 门禁改动需由你核对实际合并结果。 完成后 Agent 汇报效果入口、验收证据和交付状态。

  • 看阶段：大需求先讨论并交付方案，明确授权后才实施；小需求核实范围后可以直接实施。
  • 看效果：从约定入口查看已经实施的结果；例如小需求中非法邮箱会提示错误并阻止提交，合法邮箱仍可正常提交。
  • 看证据：验收逐条对应需求，验证与独立评审有结果，未执行项与阻塞明确列出。
  • 看状态：本地交付说明已合并、待你同意合并还是被阻塞；远程交付说明已提交 PR/MR 等平台合并、平台已合入并已同步还是被阻塞。同时给出分支、提交与工作区位置。

Agent 可以通过 status 汇总还差什么。下面示例表示门禁条件已满足，但没有验收清单，需求符合度仍是 unknown，不能据此宣布用户需求已经验收通过：

分支 feature/login -> main

  [ok] branch: 待合入 5685e8a474 -> main
  [ok] branch-name: 分支 feature/login 符合命名规范
  [ok] main-worktree: 主 Worktree 停在 main 且洁净
  [ok] evidence: 验证通过，主分支自验证以来新增 0 个文件，未波及已执行的检查，可直接复用
  [ok] review: 评审通过（需求符合度 unknown，工程质量 good，清单来源 无）
  [ok] plan: 属于直接实施的范围（代码改动 1 行），不需要实施授权
  [ok] gate: 本次没有改动门禁配置与规则
  [-] acceptance: 验收清单约定位置：acceptance/feature-login.md（存在时评审会核对需求符合度）

可以合并：harness merge --branch feature/login
  • 合并前的工作区检查、常规冲突处理和重新验证由 Agent 按项目规则执行。
  • 涉及用户已有改动或业务意图无法判断时，Agent 说明具体分歧，交由你决定。

执行命令与合并条件见一次任务参考。

大需求：多个分支连续交付

一个分支交付不完的需求可以拆成阶段，逐个分支按顺序交付。阶段写在方案目录的阶段文件里，默认路径模式是 docs/changes/*/stages.json，可由 intent.plan.stages 覆盖；每个阶段用 id、title、建议分支名 branch 和该阶段的验收清单 acceptance 描述。记录方案级授权前，阶段文件和全部阶段的清单都要先提交到任务分支。

{
  "stages": [
    { "id": "api", "title": "登录接口", "branch": "feature/login-api", "acceptance": "docs/changes/login/api.md" },
    { "id": "ui", "title": "登录页面", "branch": "feature/login-ui", "acceptance": "docs/changes/login/ui.md" }
  ]
}

你只需要授权一次。明确同意覆盖全部阶段后，Agent 在第一个阶段的分支上运行 harness approve --branch <分支> --yes --note "<你的原话>" --stages <阶段文件>，把方案级授权绑定到阶段文件与全部阶段清单的内容。携带授权的分支缺省对应第一个阶段，可用 --stage 指定；阶段按 id 关联分支，之后才合入的命名规则让建议分支名失效时，改用合规名称并照抄清单即可，不需要你重新授权。

一个阶段合并后，收尾检查会提示下一阶段，并给出建议分支名、要复制的清单和 harness approve --branch <新分支> --yes --from-stages <阶段文件> --stage <阶段>；这条命令不接受 --note，原话照搬方案级授权。Agent 据此建分支、复制清单并继续实施，不需要你逐个阶段表态。harness status 对阶段分支多一行 stages，显示已合入几个阶段、总数与下一阶段；全部阶段合入后这一行显示已全部合入，收尾检查也不再提示。

以下情况会停下来等你处理：

  • 阶段文件或某个阶段的清单在授权后改过，相关授权失效，需要你重新同意；其他阶段清单的修订不影响已经派生的分支。
  • 前序阶段还没合入主分支时，不能为后续阶段派生授权。
  • 远程交付下阶段是否合入以本地主分支为准，平台合并后要先运行 harness sync。
  • 收尾检查只提示下一步，不建分支、不授权、不合并；它只能降低提前停下的概率，同一状态连续拦满 stop.idleBlocks（缺省 3 次）仍会放行，发送“继续”即可恢复。

阶段文件格式与授权失效的完整规则见参考手册。

验证入口受阻时

遇到台账、依赖或命令启动问题时，Agent 先确认必要验收、失败阶段和存量证据，再核对是否有项目允许的等价定向入口。 入口失败不等于目标行为失败；真实页面的定向浏览器验收可以证明受影响交互，但页面加载、静态检查或单元测试不能代替未覆盖的交互。

有合规恢复路径就继续执行，必需 gate 仍须通过，合并前 extended 仍为可选项并如实披露。 不默认跑全量基线、不扩修无关问题；必要验收仍不可行且需要人决定时才上报。 每项结果的 reasonCode 与 blockedBy 帮助区分本项失败和前置失败导致的未执行，普通非零退出不能自动归为环境或断言问题。

已经上报的技术阻塞消除后，用 escalate resolve --id <编号> --reason <原因> --evidence <引用> 留下原因与证据并继续交付。 这不冒充用户答复，也不免除验证、评审与人工确认；详细诊断与命令见被拦截时怎么办。

验收清单

直接实施和先方案后实施的任务都要写清单，放在 .harness/acceptance/<分支名>.md，分支名里的 / 等字符换成 -，例如 feature/login 对应 feature-login.md。小任务只写适用的几条即可，每条对应测试、命令或人工验证。没有清单时评审只评工程质量；intent.mode 设为 required 时没有清单不能合并。

默认都是合并前验收。确实需要目标分支集成状态时，把条目写进“合并后验收”章节，并配置对应的 post-merge 检查；只写章节却没有对应检查时，验证会明确失败，不会让这条义务悄悄漏掉。

遗留补测

需要系统补齐既有测试时，Agent 按 .harness/rules/method-backfill-tests.md 先完整只读盘点，再用 .harness/templates/test-backfill.md 统一记录功能、已有覆盖、具体缺口、测试能力与有序批次。按风险而不是覆盖率数字排序，首批预算不能把后续缺口删掉。

补测只修改测试、夹具与必要的测试基础设施，不顺手修改生产代码。既有失败只阻塞相关候选，独立候选继续；计划完成或命令退出 0 不代表覆盖完整，交付前还要核对具体用例、断言与适用层。

UI 视觉验收

页面、组件、交互状态或响应式改动按 .harness/rules/method-ui-visual.md 先确定目标，再验证结构、内容、可访问性、关键视口与恢复状态。可使用 .harness/templates/visual-contract.md；小任务把适用字段写进验收清单即可。

功能 E2E 通过不等于视觉对齐，自动化评分不等于真实可用性，只保存当前截图也不能证明通过。按场景验证键盘、焦点与辅助技术语义；未实际检查的目标平台或视口标为 not_evaluated，不默认增加人工审批。

跨平台兼容

多平台产品涉及路径、进程、Shell、权限、编码、原生模块或平台 API 时，按 .harness/rules/method-cross-platform.md 和 .harness/templates/platform-matrix.md 记录目标平台、失败语义、环境与证据。不默认支持全部操作系统。

模拟分支与真实平台验证分记，不能互替；安装、协议注册、权限与原生能力使用最终交付形态验证。缺 Runner 或范围未知时明确列出阻塞与补验，不用本机成功或 skip 冒充通过。

提交信息

提交信息规范只在 .harness/policy.json 的 commit-message 规则里定义一处，commit-msg 钩子、verify 与 review 的前置检查、status 和合并共用同一份判定。可以直接约定描述用什么语言（lang 取 zh、en 或 any）、允许的类型、标题长度与正文格式。

git commit -m "feat(login): 支持短信验证码登录" -m "- 新增验证码发送与校验接口
- 登录页增加验证码输入"

每个 -m 是一段，多条要点要写在同一个 -m 里换行，或者用编辑器写。不合规时提交当场被拒，并列出违反的条目与示例；已经提交的要改写提交信息，再重新 verify、review。

清理任务 Worktree

默认在合并后保留任务 Worktree 和分支，因为会话可能还停在里面。需要手工清理时向 Agent 发起请求：

清理需求示例
我想清理已经完成的任务工作区。

Agent 应先给出预览，汇总可清理数量、连带删除的本机文件和跳过原因，不立即删除。用户授权安全清理后，由 Agent 逐项检查并执行，异常对象自动保留，其他安全对象继续处理；含本机文件的目录需要单独明确同意，主 Worktree、命令所在 Worktree 和验证检出会保留。详见授权与执行矩阵。

预览还会检查提交是否已合并、新任务保护、未提交文件、进程和锁定情况。详细条件和命令见清理参考。

也可以在主分支配置 worktree.autoClean: true，持续授权交付后的自动清理。每次只处理本次任务，远程交付等合入并 sync 后才执行；合并后义务未关闭、有本机文件、进程不可知或其他条件不满足时保留。配置改动仍需人工确认。
