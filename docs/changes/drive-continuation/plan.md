# 无人值守续跑驱动器 harness drive

- 验收清单：`docs/changes/drive-continuation/acceptance.md`
- 任务分级：先方案后实施。
  理由是新增命令与会话驱动能力，改动跨 CLI、适配器、会话记录与安全规则多个模块，并需要新增门禁规则。

## 背景

告警中心四阶段实施中，会话反复停下，用户每次都要手动输入“继续”。
升级到 0.21.0 后，收尾检查把“缺验证、缺评审”换成按进度措辞，并在同一状态拦三次，阶段之间也能自动接续，第三阶段确实在 3 分钟内开工。

但 2026-11-17 20:58 的第三次停下暴露了收尾检查管不到的一类中断：
这一轮以 `API Error: Upstream request failed` 结束，Claude Code 触发的是 `StopFailure` 而不是 `Stop`。
`StopFailure` 在客户端里是 fire-and-forget，钩子的输出与退出码都被忽略，harness 没有任何手段让这一轮继续。

## 三类中断与各自的解法

| 中断类型 | 触发 | 收尾检查能否处理 | drive 的处理 |
| --- | --- | --- | --- |
| Agent 自己以文字汇报结束一轮 | Stop | 能，最多拦 `stop.idleBlocks` 次 | 进程退出后按欠项再开一轮 |
| API 错误、上下文耗尽、客户端崩溃 | StopFailure 或进程直接退出 | 不能 | 进程退出后按欠项再开一轮 |
| 阶段之间没有待办 | Stop | 0.21.0 起能，按阶段文件续跑 | 不依赖，仍以欠项为准 |

共同点：会话停止之后，判断“还要不要继续”的权力应该留在 harness，而不是留给模型或客户端钩子。
这正是 drive 的定位。

## 目标与非目标

目标：

- 会话因任何原因停止后，只要 harness 判定还有 Agent 能接着做的欠项，就自动再开一轮。
- 判定为完成、需要人处理或连续无进展时停下，并明确告诉用户为什么停。
- 用户始终能看到 drive 写进会话的进度，并能随时接管。
- 支持所有主流编码智能体：内置 Claude Code 与 Codex 适配，第三方客户端用命令模板接入。

非目标：

- 不自动执行 `harness approve`、`harness confirm`、`harness escalate resolve` 这类必须由人或用户授权完成的动作。
- 不替代收尾检查：交互式会话里的拦截仍由 Stop 钩子负责，drive 只负责跨进程续跑。
- 不在 drive 内部实现权限审批：权限模式原样交给客户端。
- 不改变验收、评审、合并的门禁语义。

## 设计

### 一、会话模型：默认续原会话，用户看得见

- drive 默认续跑**原会话 ID**：`claude -p --resume <会话> ...`。
  这样用户在终端里用 `/resume` 或 `claude --resume <会话>` 就能看到 drive 写进去的每一轮，进度不会消失。
- 每轮结束后 drive 在自身终端打印一行摘要：本轮结果、当时欠项、下一轮要做什么。
  用户 `tail -f` 日志或看终端即可，不必打开 UI。
- `harness drive --status` 显示当前运行状态：会话、轮次、最近一轮时间、欠项、空闲轮数。
- 同一会话的排他：drive 启动前检查会话是否被其他进程占用（本机锁文件加客户端进程探测），占用时拒绝启动并说明。
  运行中若用户接管（会话被重新打开），drive 在下一轮开始前停下并提示“已由用户接管”。
- `--fork` 可选：基于原会话分叉出新会话，原会话完全不动。
  分叉时会话 ID 变化，harness 的会话分支记录原本不认识新 ID，drive 负责把原会话记录的分支集合复制到新会话。
  这条是 `--fork` 额外要做的，默认路径不需要。

### 二、循环判定：以 harness 的欠项为准

每轮结束后，drive 用与收尾检查相同的一套读取计算欠项，不重新发明判定：

- 读该会话经手的任务分支，调用现有的状态计算，得到每个分支的欠项与“是否要等人工处理”。
- 三态：
  - **继续**：存在 Agent 能接着做的欠项（缺验证、缺评审、未提交、未合并、下一阶段没开始等），且没有上报阻塞。
  - **完成**：没有欠项。
  - **要人**：只差用户同意实施、门禁改动确认、上报未解除、方案级授权失效这类人来做的事。
- 停止条件按优先级：完成、要人、连续无进展、连续失败、达到轮次上限、被用户接管、收到终止信号。
- 无进展判定复用现有指纹：分支顶端、阻塞项、未提交文件内容与欠项文案。
  连续 `maxIdleRounds` 轮指纹不变就停，避免空转烧钱。
- 每轮的启动提示固定写成一条：当前欠项清单与下一步，要求以工具调用推进，不要只用文字汇报结束。
  内容由 harness 生成，不依赖模型自己回忆。

### 三、通用性：适配器与命令模板

- 适配器接口只有三件事：拼出命令、从输出里取回会话 ID 与最终结论、判断本轮是否成功。
- 内置两种：
  - `claude`：`claude -p --resume <会话> --permission-mode <模式> --output-format json`，从 JSON 结果取会话 ID 与最终文本。
  - `codex`：`codex exec resume <会话> --json`，从 JSONL 事件取线程 ID 与最后一条消息。
- 第三方客户端用命令模板接入，模板里支持 `${session}`、`${prompt}` 两个占位符，输出解析方式选 `json`、`jsonl` 或 `text` 之一。
  这样 Cursor CLI、Gemini CLI 或自研 Agent 都能接，不需要为每个工具写代码。
- 客户端配置放在本机文件 `~/.config/harness/drive.json`，不进仓库，也不受项目门禁篡改。
  项目侧只在 `.harness/config.json` 增加一个可选项 `drive.client` 与 `drive.permissionMode`，缺省 `claude` 与 `bypassPermissions`（按用户选择）。

### 四、权限与安全

- 权限模式按用户选择缺省为 `bypassPermissions`，即无人值守运行不做权限审批。
  这一项必须显式可见：drive 每次启动都在首行打印“客户端、会话、权限模式、轮次上限”，用户能看到自己在授权什么。
- harness 的实时拦截与收尾检查照常生效，和权限模式无关：`bypassPermissions` 只跳过客户端自己的确认框，不跳过钩子。
  实施时用一条真实用例确认 `-p` 模式下 PreToolUse 钩子确实会执行，这条不能只靠推断。
- 新增门禁规则：`harness drive` 只能由人启动，Agent 自己运行会被拒绝。
  理由是它是唯一能让 Agent 在无人监督下连续多轮的开关，等价于把“继续”的授权永久开下去。
- drive 自身不执行任何需要人工确认的命令：
  不调用 `harness approve`、不调用 `harness confirm --yes`、不解上报。
  子进程里 Agent 若尝试这些，仍由 `gate-self` 规则拦截。
- 预算与失败保护：`maxRounds` 缺省 40、`maxIdleRounds` 缺省 3、`maxFailures` 缺省 3。
  客户端支持花费上限时透传 `--max-budget-usd`，缺省由用户配置给出，不给就用客户端自己的默认值。

### 五、进度可见与通知

- 终端：每轮一行摘要，停止时打印停止原因与“接着怎么办”的一条命令。
- 账本：每轮写一条 `drive.round`，停止时写一条 `drive.stop`，记录会话、轮次、欠项快照、停止原因。
- 可选通知命令：`notify` 配置里给一个命令数组，停下时执行一次，`${reason}`、`${session}`、`${rounds}` 三个占位符。
  macOS 下用户可以填 `osascript -e 'display notification ...'`，Linux 下填 `notify-send`，不填就不通知。
- `harness status` 增加一行：最近一次 drive 的会话、停止原因与时间，避免用户忘了它在跑或已经停了。

## 兼容性与默认行为

- 不安装、不启用 drive 时，harness 的全部行为与 0.21.0 一致：没有新配置就没有新输出。
- `harness drive` 是新增命令，不影响现有命令的参数与输出。
- 新增的门禁规则只拦 `harness drive`，不影响其他命令。
- 新增配置项都有缺省值，缺省值与“不配置”等价。

## 已知限制

- 续跑同一会话依赖客户端把多轮写进同一份记录；客户端若默认不落盘（例如 `--no-session-persistence`），drive 必须拒绝启动。
- harness 无法判断一轮为什么失败：API 错误、客户端崩溃、用户手动中断都表现为进程退出，drive 只能按“欠项还在就再试”处理，并靠连续失败上限兜底。
- 分叉后再合并回原会话不可能，`--fork` 之后原会话的进度到此为止。
- 无人值守运行 `bypassPermissions` 时，任何客户端本身允许的危险操作都只由 harness 的规则拦截；规则没覆盖到的动作会被执行。
- 用户接管检测是启发式：客户端进程探测不到时，可能出现两边同时续跑同一会话。
