# 本机跨项目只读 Dashboard

- 状态：设计稿，本次只交付方案与验收文档，实施另需授权。
- 验收清单：`docs/changes/local-dashboard/acceptance.md`。
- 任务分级：先方案后实施。
  理由是新增本机项目注册表、跨项目观测数据契约和 HTTP 服务，涉及本机数据边界与长期兼容。

## 背景

harness 已在每个仓库的共享 Git 数据目录中保存证据、评审、确认和追加式账本 `ledger.jsonl`。
现有 `metrics` 能按周展示单项目的验证、评审、交付与策略拒绝指标，`doctor` 和 `conformance` 能报告当前接入与配置状态。
这些能力仍不足以回答本机多个项目的活跃度差异、流程趋势、反复阻塞点和配置改进空间。
用户目前需要逐项目运行命令并自行汇总，命令行文本也不适合承载多维比较与下钻分析。

本方案增加本机只读可观测性层和按需启动的 Web Dashboard。
Dashboard 不是门禁控制台，不参与证据判定，不替代现有 CLI，也不把内部项目数据发送到外部服务。

## 问题澄清

| 问题 | 结论 |
| --- | --- |
| “本机所有项目”是否意味着自动扫描整个磁盘 | 否。首版只覆盖已登记项目，已有项目由用户显式登记，不默认递归扫描用户目录。 |
| 同一仓库的多个 Worktree 是否算多个项目 | 否。以规范化后的 Git common dir 去重，主 Worktree 作为默认展示路径。 |
| “使用频率”是否包含全部 Agent 工具调用 | 否。首版统计验证、评审、交付和策略拒绝等流程活动，不从现有账本推导全部工具调用次数。 |
| 策略拒绝次数能否直接换算工具调用拦截率 | 不能。现有数据没有全部允许调用的分母，首版只展示拒绝次数及按活跃日等口径归一化的计数。 |
| `submit.ready` 是否表示任务已经合入平台主分支 | 否。它表示 PR/MR 已就绪，与本地 `merge` 和后续 `sync` 分开统计。 |
| Dashboard 能否展示配置问题的历史持续时间 | 首版不能。当前 `doctor` 只有本次读取结果，健康历史需要后续显式采样快照。 |
| 没有事件是否表示项目从未使用或没有失败 | 不一定。必须区分无活动、无数据、读取失败、未登记和数据覆盖不足。 |
| 只读是否意味着 Dashboard 不能写任何本机文件 | 只读指不改项目、账本、证据和门禁状态。注册表及后续自有快照可以写在 harness 的用户级目录，并清楚标识副作用。 |
| 是否让 `doctor` 隐式登记项目 | 首版不让诊断命令承担该副作用。登记放在 `init`、`install` 和显式项目登记入口。 |
| Web 服务是否需要常驻或随系统启动 | 不需要。首版由 `harness dashboard` 按需启动，命令退出后服务结束。 |
| 是否拆成独立仓库或 npm 包 | 不拆。首版同仓库、同版本发布，用模块目录和单向依赖隔离职责。 |
| 是否引入数据库和前端框架 | 首版不引入。只有实际数据规模或交互复杂度证明现有方案不足时才重新评估。 |
| 是否提供 Web 合并、确认、验证或配置编辑 | 不提供。页面只展示证据、解释和建议命令，不执行门禁写操作。 |

## 目标

- 汇总当前用户明确纳入范围的本机 harness 项目，并正确处理 Worktree 去重和项目失联状态。
- 展示各项目关键流程的使用次数、活跃天数、执行结果、耗时、已记录成本和数据覆盖范围。
- 支持单项目与跨项目的 7、30、90 天滚动窗口及周趋势。
- 比较项目配置、版本、交付模式、验证与评审结果，同时展示样本数和背景信息。
- 复用 `doctor`、`conformance` 和账本中的确定性证据，给出可复核的问题说明与建议 CLI 命令。
- 为 CLI 和 Web 提供同一份版本化 JSON 读模型，避免网页解析人类可读输出。
- 保持现有门禁流程独立可用，Dashboard 故障或关闭不影响验证、评审与交付。

## 非目标

- 不记录或推断完整的工具调用、会话时长、源码内容和在线行为。
- 不把本地账本当作完整、不可抵赖的审计日志。
- 不生成跨项目综合健康分或项目排行榜。
- 不自动判断拦截频繁就是配置错误，也不把相关性描述成因果关系。
- 不在首版提供持续健康监控、定时采集、实时推送、远程访问或多人协作。
- 不在打开页面时运行测试、黄金任务、评审、模型请求或远程平台查询。
- 不重写历史账本，不要求既有项目先升级才能被读取。
- 不改变现有门禁、授权、人工确认、交付和版本发布语义。

## 已确认的架构决策

- 产品定位是“本机研发流程可观测性”，不是“Web 版门禁控制台”。
- 服务默认只监听 `127.0.0.1`，使用随机端口，默认只读且不开放跨域访问。
- 首版使用 Node.js 标准库和静态 HTML、CSS、JavaScript，不新增第三方运行时依赖。
- 通用数据层与 Web 展示层分目录，核心门禁流程不依赖 Dashboard。
- 新事件逐步采用版本化契约，聚合器兼容旧事件，不迁移或重写原账本。
- 项目配置继续以主分支固定提交为信任来源，不能读取任务分支配置冒充当前生效配置。
- Dashboard 不参与门禁判定，不能调用 `merge`、`submit`、`confirm --yes` 或其他写操作来绕过 CLI 边界。

## 模块与目录

```text
src/
  observability/
    projects.mjs          # 项目注册、去重、显式登记与状态核对
    ledger.mjs            # 无副作用的数据目录定位、账本读取和旧事件适配
    aggregate.mjs         # 跨项目指标、数据质量和时间窗口
    snapshot.mjs          # 版本化 JSON 读模型
  dashboard/
    command.mjs           # harness dashboard 命令与进程生命周期
    server.mjs            # 回环 HTTP 服务和访问控制
    routes.mjs            # 固定只读路由

assets/
  dashboard/
    index.html
    dashboard.css
    dashboard.js

test/
  observability.test.mjs
  dashboard.test.mjs
```

`observability` 是通用数据层，同时服务 CLI 和 Web。
`dashboard` 只是读模型的一种展示方式，不拥有指标定义，不直接遍历项目文件，也不复制一套聚合逻辑。
`src/golden/metrics.mjs` 中已有的通用计算应由 CLI、现有 `conformance` 和新数据层共享；实施时可逐步抽取公共逻辑，不做与该能力无关的大规模移动。

依赖方向如下：

```text
CLI ───────────────→ observability
CLI → dashboard ───→ observability
observability ─────→ 只读配置、账本、doctor、conformance

核心门禁流程 ──不依赖──→ dashboard
```

目录隔离只是维护边界。
真正的安全边界由只读接口、字段白名单、固定静态资源映射、HTTP 访问控制和不调用门禁写操作共同保证。

## 本机项目注册表

### 存储与身份

- 在当前用户的 harness 数据目录维护 `projects.json`，不与项目入库配置混放。
- 注册表包含 `projectId`、规范化 `commonDir`、主 Worktree、展示名、首次与最近登记时间、最近已知 harness 版本和状态。
- `projectId` 是 Dashboard 的稳定关联标识，规范化 `commonDir` 是首版的 Worktree 去重键。
- 同一 `commonDir` 只产生一个项目，不能因多个工作区路径重复计数。
- 不凭目录 basename 或远程地址自动合并项目，避免同名仓库和 fork 被误并。
- 注册表更新采用原子替换并处理并发，文件权限仅允许当前用户读写。
- 注册失败不影响门禁和项目命令，后续读取时明确显示登记数据不完整。

### 登记与生命周期

- `init` 和 `install` 在已有安装流程中登记或更新项目。
- 首版提供显式单项目登记入口，供已有项目纳入范围。
- 递归发现只能在后续由用户指定根目录后显式执行，不默认扫描整个用户目录。
- `uninstall` 将项目标为已卸载并保留历史，不删除已采集指标。
- 路径不存在、权限不足或不再是 Git 仓库时分别标记失联、不可读或无效，不从页面静默消失。
- 仓库整体移动后由用户显式重新绑定新旧路径；没有可靠身份证据时不自动合并历史。
- 最近活动从账本事件计算，不为刷新 `lastSeenAt` 在每次客户端钩子中额外写注册表。

## 数据源与只读采集

| 数据源 | 首版用途 | 限制 |
| --- | --- | --- |
| 项目注册表 | 项目范围、路径、状态和 Worktree 去重 | 未登记项目不在覆盖范围内 |
| 各项目 `ledger.jsonl` | 流程次数、结果、时间、耗时和已记录成本 | 尽力写入且未签名，可能缺失、损坏或重复 |
| 主分支固定提交中的 `.harness` 配置 | 配置摘要、交付模式、规则和检查数量 | 不使用任务分支配置替代生效配置 |
| `doctor` | 当前安装、客户端钩子、版本、评审者和检查配置状态 | 没有历史快照，不进行远程查询 |
| `conformance` | 当前配置、行为和稳定性判据 | 样本不足保持 pending，不改造成综合分数 |
| 现有签名记录 | 按需展示当前记录有效性和数据问题 | 不输出签名密钥、原始报告或任意文件内容 |

新增只读数据目录定位函数，不能复用会创建目录或归属文件的 `dataDir()` 作为 Dashboard 的读取路径。
读取账本、打开页面和刷新页面都不能创建项目数据目录、生成密钥或修改证据。
单个项目发生解析、权限或版本兼容错误时，其结果降级为该项目的数据警告，其他项目仍可查看。
首版可复用现有整文件解析思路；出现可测的内存或延迟问题后，再增加流式、事件去重索引或增量读取。

## 事件契约与历史兼容

新事件逐步使用统一外层字段：

```json
{
  "schema": 1,
  "id": "event-id",
  "at": "2026-11-27T00:00:00.000Z",
  "event": "verify",
  "projectId": "project-id",
  "outcome": "passed",
  "harnessVersion": "<version>"
}
```

- 业务字段按事件类型使用白名单，不新增原始命令、提示词、会话正文、报告全文和未经脱敏的错误输出。
- 事件 ID 用于新事件去重，缺失 ID 的旧事件按原顺序读取并标记无法可靠去重。
- `projectId` 由聚合器结合注册表校验，不能仅相信账本内自报字段。
- 读取器容忍旧字段、缺少版本和未知事件，未知事件进入覆盖范围说明而非导致全局失败。
- 旧账本保持原样，迁移只发生在内存中的读模型。
- 新事件写入失败仍遵循账本不影响门禁的现有原则，页面必须能表达这种覆盖限制。

## JSON 读模型与命令边界

CLI 和 Web 共用版本化快照，至少包含：

```text
schemaVersion
generatedAt
timeRange
projects[]
metrics
coverage
warnings[]
```

`coverage` 至少描述登记项目数、成功读取数、失败数、各项目事件时间范围、未知事件数、无法去重的旧事件数和统计口径限制。
`warnings` 使用稳定的机器码与脱敏详情，页面不能只依赖自然语言匹配问题类型。

首版命令行为如下，具体帮助文本随实现纳入现有 CLI 契约测试：

- `harness projects list --json` 列出当前用户已登记项目及状态。
- `harness projects add <路径>` 显式登记一个已有仓库，重复登记同一 common dir 保持幂等。
- `harness metrics --all --days 30 --json` 输出跨项目聚合；不带 `--all` 时保留当前单项目行为。
- `harness doctor --json` 输出当前项目的结构化诊断，不使用 `--check-remote` 时仍不访问远程。
- `harness dashboard` 启动本机服务并输出访问地址，可由用户选择是否打开浏览器。

HTTP 首版只需静态资源和一个版本化只读快照端点。
不新增公开 `dashboard-data` CLI 命令，也不让页面解析 `metrics`、`doctor` 的文本格式。
退出码、stdout 与 stderr 继续遵守现有 CLI 约定，Web 服务访问地址和诊断不能被 JSON 数据污染。

## 指标口径

### 时间

- 事件时间保存为 ISO 时间戳，计算使用明确的时间点，不使用服务器本地日期字符串推断。
- 7、30、90 天是以 `generatedAt` 向前计算的滚动窗口，页面显示起止时间。
- 周趋势首版沿用现有 UTC 周一作为周边界，并在页面标注，避免与现有 CLI 隐式产生两套周口径。
- 指标计算接受固定当前时间作为测试输入，测试不能依赖真实时钟造成边界不稳定。

### 验证

- 正式验证次数只统计 `verify`，定向 `verify.targeted` 单独展示。
- 首过率的单元是 `(projectId, tree)`，从该单元完整历史中的第一次正式 `verify` 判定，再按第一次验证时间归入滚动窗口。
- 窗口内重跑不能重新进入首过率分母。
- 探索性操作、定向验证和缺少有效 tree 的旧事件不进入首过率，并计入相应覆盖说明。
- 验证耗时同时保留总耗时、平均数和中位数；样本过少时不展示高分位数结论。
- 跨项目首过率使用总首次通过数除以总首次验证单元数，不对项目百分比取简单平均。

### 评审

- 正式评审拒绝率只统计正式完成的 `review`，探索性评审和 `review.preflight` 分开计数。
- 评审成本只汇总已有有效数值的事件，缺失成本记为未知，不按零成本解释。
- 评审者、模型和端点只在确有帮助且符合字段白名单时展示，端点和内部地址默认不出现在跨项目总览。

### 交付与策略

- `merge`、`submit.ready` 和 `sync` 分别表示本地合并、远程请求就绪和本地主分支快进，不相加为“完成交付总数”。
- 按已交付任务归一化时只使用能够可靠关联的任务，无法关联的记录进入覆盖说明。
- 策略拒绝只提供绝对次数、规则与客户端分布，以及明确命名的每活跃日计数。
- 不计算 `policy.deny / 全部工具调用`，也不把高拒绝次数直接判为配置不佳。
- `merge.post_failed` 表示主分支更新后的同步命令失败，与待完成的合并后验收义务分开命名和展示。

### 空值与样本

- 分母为零时比率为 `null`，页面显示“暂无样本”，不是 `0%`。
- 无数据、无活动、读取失败和数据过期使用不同状态。
- 比率旁同时展示分子和分母，趋势中没有样本的区间不补零。
- 稳定性判断继续尊重现有 `conformance` 的样本要求，不另设未经验证的跨项目达标阈值。

## 页面范围

### 总览

- 已登记、近期活跃、失联、不可读和读取失败的项目数。
- 7、30、90 天流程活动量、正式验证、评审、本地合并和远程请求就绪次数。
- 验证首过率、评审拒绝率、策略拒绝次数、合并后同步失败次数、已记录评审成本和验证耗时。
- 数据覆盖率、生成时间、旧事件限制和异常项目数量。

### 项目比较

- 活跃天数、最近活动时间、每活跃日流程事件数。
- 能可靠关联时，展示每个已交付任务对应的验证和评审次数。
- 验证首过率、评审拒绝率、策略拒绝计数、验证耗时和合并后同步失败率，均附样本数。
- harness 版本、delivery 模式、规则与检查数量、评审配置摘要和当前健康状态。
- 默认不按绝对次数排序为优劣排名，用户可按明确列排序并看到指标定义。

### 项目详情

- 当前生效配置摘要及配置来源提交。
- 当前 `doctor` 与 `conformance` 结果，明确这是采集时点状态。
- 最近验证、评审和交付时间线，以及失败检查和重复出现的问题。
- 待完成的合并后验收义务和能够读取的数据质量问题。
- 路径移动、项目删除、权限不足、账本损坏和签名记录失效分别显示。

### 问题与改进

首版只提供可由现有证据支持的提示：

- 项目未完整接入客户端钩子，或 Codex 钩子尚未信任。
- 版本锁定不一致、安装完整性失败或项目长期锁定旧版本。
- 没有可自动执行的检查、黄金任务长期未运行或最近未全部通过。
- `extended` 检查缺少补验说明，或存在到期未登记的合并后验收。
- 同一检查、评审预检或评审发现反复出现。
- 某条策略拒绝集中在特定项目或客户端，建议复核规则与实际工作方式。
- 项目之间的关键配置存在差异，只列差异和可能影响，不自动要求统一。

每条提示包含证据、样本范围、不确定性、建议命令和对应项目链接。
页面不替用户执行建议命令，也不调用在线模型生成无法复核的诊断。

## HTTP 与隐私边界

- 服务只绑定回环地址，使用随机端口；显式端口仅作为本机可选参数。
- 每次启动生成随机访问令牌，API 请求必须携带令牌，令牌不写入项目、账本或普通日志。
- 校验 `Host` 和 `Origin`，不设置允许跨域读取的响应头。
- 首版只支持必要的 GET 请求，其他方法拒绝；快照与详情响应使用 `Cache-Control: no-store`。
- 静态页面使用限制性 CSP，不加载第三方脚本、字体、图片或分析服务。
- 静态资源只映射 `assets/dashboard/` 内的固定文件，API 不接受任意文件系统路径。
- 输出使用字段白名单和既有脱敏能力，但不得把启发式脱敏当作完整凭据识别保证。
- 默认不返回原始命令、报告、错误全文、用户授权原话和会话内容。
- HTTP 路由和前端不直接读取或返回 `evidence.key`，签名状态只通过现有校验接口取得，不开放项目目录浏览。
- Dashboard 自有注册表、快照和缓存只写当前用户级 harness 目录，权限为仅当前用户可读写。
- 不自动注册 launchd、系统服务或开机启动，不留常驻后台进程。
- 页面不触发远程平台查询；后续健康采样若需要定时任务，必须另行设计与授权。

## 兼容性与降级

- 未安装 Dashboard 新版本的旧项目仍由聚合器按注册信息读取旧账本。
- 项目锁定版本可以不同，读取器不能把本机当前 CLI 版本当成事件产生版本。
- 项目损坏或不可读时按项目隔离错误，总览继续提供其他项目结果。
- Web 静态资源加载失败不影响 CLI 的 JSON 输出。
- HTTP 启动失败只影响 `dashboard` 命令，不影响核心门禁。
- 后续缓存损坏时可以删除并重建派生缓存，原账本和注册表不被当作可删除缓存。
- 现有 `metrics` 文本输出保持兼容；如调整首过率窗口错误，应同时更新 CLI 与 Web 的共享测试并说明行为变化。

## 分阶段实施

| 阶段 | 范围 | 完成判据 |
| --- | --- | --- |
| 一、数据基础 | 项目注册与 Worktree 去重、纯只读采集、旧事件适配、数据质量、共享指标修正、JSON 输出 | 跨项目与单项目口径一致，损坏和缺失可解释，CLI 契约测试通过 |
| 二、Dashboard MVP | 按需 HTTP 服务、访问控制、静态页面、总览、比较、详情和问题列表 | 只读本机，无外部请求，7/30/90 天与空态正确，真实多项目走查通过 |
| 三、分析质量 | 显式健康快照、配置演进、可靠任务关联与流程漏斗、事件去重和按需增量读取 | 每项有新增数据源或实测依据，不把推测写成事实 |

阶段一必须先完成，不能先写页面再补数据口径。
阶段二只使用阶段一稳定的 JSON 读模型。
阶段三按实际使用价值拆成独立任务，不与 MVP 捆绑交付。

## 测试与验收

测试沿用 `node:test`、`node:assert` 和 `test/helpers.mjs` 的隔离仓库，不依赖真实凭据或在线服务。
先以合成账本覆盖已知事件、旧事件、重复事件、跨窗口重跑和损坏输入，再用隔离的多个真实 Git 仓库验证注册、读取、JSON 和 HTTP 端到端行为。
HTTP 测试使用随机回环端口和真实请求，不只测试路由函数。
前端至少在浏览器中验证总览、筛选、项目下钻、空态、错误态和无横向溢出的常用视口。
完整验收见同目录的 `acceptance.md`。

## 风险与恢复

- 注册表遗漏项目会造成覆盖偏差，因此页面必须展示登记范围并提供显式登记入口。
- 账本缺失和重复会影响指标可信度，因此首版不承诺完整审计，并展示无法去重等限制。
- 跨项目比较容易产生错误归因，因此保留样本、配置背景和不确定性说明，不提供综合排名。
- 本机 HTTP 仍可能暴露私有元数据，因此访问令牌、回环绑定、Origin 校验和字段白名单是 MVP 必需项，不是后续加固。
- 项目数和账本增长可能造成读取延迟，先测量再引入缓存，不能为预期规模提前增加数据库。
- 数据层改动集中在新增模块及现有指标的窗口语义，出现问题时可停用新命令并恢复共享指标实现，原账本、证据与门禁记录不需要回滚或迁移。

## 决定记录

- 采用按需启动的本机只读 Dashboard，不做常驻服务。
- 采用同仓库、同版本的 `src/observability/` 与 `src/dashboard/` 模块隔离，不拆独立包。
- 用户已确认上述独立目录方案。
- 首版只统计关键流程活动，不记录每次工具放行。
- 项目注册优先于页面实现，已有项目显式登记，不默认全盘扫描。
- 稳定 JSON 读模型优先于 Web UI，CLI 与 Web 共用数据层。
- 数据覆盖率、样本数和读取失败属于首版必需信息。
- 配置健康历史、任务漏斗、实时刷新和写操作均不进入 MVP。
- 本次没有功能实施授权，不修改版本号与 CHANGELOG，不打标签，发版另行授权。
