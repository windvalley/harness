# 合并后验收：义务不丢（PR1 最小版）

## 概要

0.16.0 的合并后验收把"还欠哪些验收"存在分支当前顶端提交的证据里，导致义务会在多种情况下悄悄消失。
本方案只修这一类缺陷：合入时为每项待验收检查写一条独立的义务记录，由记录而不是分支顶端决定"还欠什么"。
只新增一种记录，不新增配置字段，不新增执行路径。
未配置 `post-merge` 检查的项目不写记录，所有新增代码路径都不会执行，行为与 0.16.0 一致。

## 要修的缺陷

第 1 种已由我在临时仓库复现；第 2 到 4 种来自独立评审的复现与代码分析（第 4 种是 `status.mjs` 把验签失败当作没有义务），实施时先用测试复现再修。

1. 合入后在原分支追加一个不命中 `when` 的提交并再次合入，`status` 显示"无需再交付"，待验收义务消失。
2. 合入后对同一分支再跑一次 `verify`，证据被覆盖，义务随之消失。
3. 删除已合并的分支后，收尾检查在 `branch_missing` 处直接放行。
4. 密钥轮换后，验签失败的证据被当作没有义务。

另有两个可见性缺口：

5. `merge` 只在 stdout 的 JSON 里列出待验收项，可读输出不提示；`sync` 完全不提示。
6. 合并后验收待完成时 `harness status` 仍返回退出码 0，脚本与无钩子的客户端无法感知。

## 数据模型

新增一种签名记录 `obligation`，每项待验收检查一条。

- 键：`ob-<sha256(检查ID + 交付时的分支顶端)前 24 位>`。
  用分支顶端而不是分支名，分支名复用或同一分支多次合入时记录不会互相覆盖。
- 字段：检查 ID、分支名、分支顶端、检查定义快照（含 `howToVerify`）、创建时间、`closedBy`（未关闭为空）。
- `closedBy` 记录关闭它的那次登记：主分支提交 `at`、登记时间、报告 SHA-256。

不新增"运行记录"。
没有失败状态时，登记记录就是现有的 `attestation`，关闭结果直接写在义务上，轮换密钥后重签即可，不会成批重开。

## 状态与对账规则

- **何时写**：本地交付在 `merge` 更新主分支之前、锁内写入；远程交付在 `submit` 成功后写入。
  只在本次证据的 `postMerge` 列表非空时写。
  合并没有真正完成时，记录的分支顶端还不是主分支的祖先，所以不会到期，无害。
  已存在且已关闭的同键记录不覆盖，重复 `merge` 或 `submit` 不会让它重新打开。
- **何时到期**：义务的分支顶端是当前主分支的祖先。
  远程交付里平台用 squash 或 rebase 合入时，这条判断认不出已合入，义务保持不到期，只会显示。
  这是 0.16.0 就有的限制，本方案不改变它，见"暂缓与另行处理"。
- **何时关闭**：一次 post-merge 登记成功时，找出同一检查 ID、尚未关闭、分支顶端是 `at` 的祖先的全部义务，一并关闭。
  `at` 默认是登记时的主分支提交，可用 `--at <提交>` 指定为实际被测的那个提交，必须是当前主分支的祖先。
  这条规则让重试、修复分支登记后关闭原分支、并行合入、同一分支多次合入使用同一套逻辑，不再需要 `--resolves`。
  `--at` 防止"测试之后、登记之前又有任务合入"时，把没测过的义务误关。
- **按检查 ID 关闭，不比对定义指纹**：关闭看的是"检查 C 在主分支 M 上通过"。
  定义快照只用于显示 `howToVerify`。
- **待办的判定**：到期且未关闭，即为待办。
  记录存在但验签失败时同样按待办处理，并在提示里说明原因，不当作没有义务。
- **读取时转换**：没有义务记录、但分支顶端的证据里有 `postMerge` 列表时，读取时按同一结构推导出义务，参与同一套对账。
  只保留一套对账逻辑，不做数据迁移。

## 默认关闭的依据

- 记录只在证据 `postMerge` 非空时才写，没有配置 `post-merge` 检查就不会产生记录。
- `status`、`sync`、`stop` 对义务的读取都以"存在义务或证据里有 `postMerge`"为前提，否则直接返回，不新增输出。
- `status` 的退出码只在存在待办时变化。
- 不改动会话分支登记，不改动 `worktree clean`，不改动 `sync` 判断合入的方式。
- 新增的 `--at` 与 `status --post-merge` 都是新参数或新子模式，不影响已有调用。
- 基线测试必须断言：不配置时不产生 `obligation` 记录，各命令的输出与 0.16.0 逐字一致。

## 验收标准

1. 不配置 `post-merge` 检查时，全流程输出与 0.16.0 一致，且数据目录里没有 `obligation` 记录。
2. 上述缺陷 1 到 4 每一种都有一个 CLI 集成测试，修复前失败、修复后通过。
3. 本地交付：`merge` 的可读输出列出待办；登记后 `status` 显示完成，退出码 0。
4. 远程交付：`submit` 后写入义务；平台合入并 `sync` 后 `sync` 输出待办，登记后关闭。
5. 并行合入：两个分支先后合入，`--at` 指向第一个之后的主分支提交时，只关闭它包含的义务。
6. 修复分支登记后，原分支的义务一并关闭。
7. 非快进合并下义务正常到期与关闭。
8. 0.16.0 遗留的、只有证据没有义务记录的待验收任务，读取时被推导出来并可关闭。
9. 使用非 Web 项目夹具（例如命令行工具或库），不依赖前端与部署环境。
10. `status --post-merge` 在没有任何义务时输出为空且退出码 0。

## 暂缓与另行处理

下面的事项不进入 PR1，各自写明触发条件。

| 事项 | 为什么不放进 PR1 | 触发条件 |
| --- | --- | --- |
| `attest --status failed` 与连续三次转上报 | 新增状态与计数。`core.md` 已规定同一问题连续三轮要停下上报，先靠规则文件约束 | 有项目实际出现合并后验收反复失败，仅靠规则无法约束 |
| `verify --post-merge`（harness 自己执行 `cmd`） | 新增执行路径、仓库锁、超时、环境与凭据边界，是最大的新增面 | 有项目明确要求证据不靠自述 |
| 远程 squash 与 rebase 合入的识别 | 0.16.0 就存在的独立缺陷：`status` 会误报 `review_stale`，`attest` 被拒。修复会改变不配置项目的行为，与"默认不变"冲突 | 单独作为缺陷处理，需要你明确接受行为变化 |
| 命令与备注的脱敏 | 现有 `redact` 盖不住 `--token` 后面的值，合并前登记的命令原样进入评审提示。这是对所有使用 `attest` 的项目的安全缺陷，与合并后验收无关 | 单独作为安全缺陷处理，需要你明确接受显示变化 |
| 会话分支登记加入 `attest` 与 `sync` | 会让只做过合并前登记的会话被收尾检查追着合并，且 `sync` 没有 `--branch`，加入无效 | 不做 |
| 检查级 `maxFixRounds`、`target`、`revision`、`covers`、`scopeMap` | 隐含部署环境、版本号、清单条目标识等假设，与 `when` 重复，且只是比对 Agent 自述 | 不做 |
| `worktree clean` 跳过有待办义务的分支 | 义务已与分支解耦，跳过只会留下无用的 Worktree | 不做 |

## 风险

- `attest` 仍是自述证据：harness 只存命令文本与报告哈希，不核对命令是否真的跑过、跑在哪个版本。
- 远程交付下平台用 squash 或 rebase 合入时，义务不会到期，只能在 `status --post-merge` 里看到，不会被收尾检查拦下。
- 按检查 ID 关闭意味着一次通过会关闭所有更早合入的同检查义务。
  这是"检查 C 在主分支 M 上通过"的字面含义，但并行任务的范围差异由人在清单里写明，harness 不判断。
- 读取验签失败的记录时仍需要能解析其内容，关闭时用新密钥重签。
  这与 `attest` 本身的信任等级相同，不新增信任边界。

## 待确认

1. 按检查 ID 关闭、不比对定义指纹，是否接受。推荐接受，原因见上。
2. `status` 在合入但有待办时退出码改为 1，是否接受。它只在配置了 `post-merge` 的项目里生效。
3. 远程 squash 识别与脱敏是否各自单独立项。推荐单独立项，各自升版本并写明行为变化。
