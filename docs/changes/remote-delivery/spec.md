# 行为说明：远程交付模式

- 验收清单：同目录的 acceptance.md
- 实施方案：同目录的 plan.md

## 问题

- 团队把主分支放在 GitHub、GitLab 等平台上，合并要走 MR/PR 和平台的保护规则。
- 现在门禁通过后只能用 `harness merge` 合入本地主分支（`src/merge/merge.mjs` 的 `mergeTask`），本地主分支会和远程分叉。
- 远程合并后把本地主分支拉回来会被 `reference-transaction` 拒绝（`src/githook.mjs` 的 `guardReference`）。
  手册只给了由人用 `HARNESS_MAIN_BYPASS` 快进的做法（`docs/reference.md` 的“与远端同步”）。
- Agent 自己推送、建 MR 时，harness 不能保证 MR 上的提交就是通过门禁的那一个，描述里也没有门禁结果。

## 目标行为

### 配置与授权

- `.harness/config.json` 新增 `delivery` 段，从主分支读取：

  ```json
  "delivery": { "mode": "local", "remote": "origin", "provider": null }
  ```

- `mode` 默认是 `local`，即现在的行为。
  取 `remote` 时 `provider` 必填，取 `github` 或 `gitlab`，分别调用本机已登录的 `gh` 与 `glab`，认证由它们负责。
- `init` 在新项目的配置里显式写出 `"delivery": { "mode": "local" }`，让用户看到有这个开关。
  已有项目没有这一段时同样按 `local` 处理，`upgrade` 不改动配置。
- 本地主分支仍是唯一的信任根，配置一律从它读取。
  远程模式下本地主分支只由 `sync` 快进，`merge` 不再写入。
- 开启远程模式即项目层面的常设授权：`submit` 可以把任务分支普通推送到配置的远程，并创建或更新 MR/PR。
  这项授权不包括平台上的合并、推送主分支、强推、部署或其他远程操作。
- 交付设置的实际变化（缺省按 `local` 计）都要人工确认，不受 `governance.confirmOnGateChange` 影响。
  确认摘要单独列出交付设置的变化和由此授予的远程权限。

### 开启与关闭

- 远程主分支通常受保护，只接受 MR/PR 合并。
  开启开关的分支如果用 `merge` 合入本地主分支，本地主分支推不上去，会和远程分叉；之后 `submit` 因为 C 不等于 B 拒绝，模式开不起来。
- 因此主分支是本地模式时，把 `delivery.mode` 改为 `remote` 的分支，在有绑定合并结果 tree 的人工确认后可以 `submit`。
  门禁核对仍按本地主分支的配置，`remote` 与 `provider` 取分支提议的值。
  做法与首次接入相同：分支提议的配置在确认之前拿不到推送权限。
- 平台合入后用 `sync` 导入，本地主分支从此是远程模式。
- 关闭不需要特殊处理：主分支是远程模式时 `submit` 本来就可用，把 `mode` 改回 `local` 的分支照常提交，平台合入后 `sync` 导入并确认。
- 主分支是本地模式、分支也没有开启远程交付时，`submit` 拒绝。

### 交付：submit

- 固定三个对象：本地主分支提交 C、本次取得的远程主分支提交 B、任务提交 H。
  要求 C 等于 B，不一致时先 `sync`。
- 门禁核对与 `merge` 共用同一段代码，结果包括预期合并结果的 tree。
  验证缺失、被主分支波及或检查配置变化时，按 0.8.2 的规则补跑。
- 源必须是本地任务分支，不能是主分支、远程跟踪引用或提交号。
  推送的是核对过的 H，不按分支名推送；核对后分支顶端变化就拒绝。
- MR/PR 描述里 harness 只维护 `<!-- harness:submit:start -->` 与 `<!-- harness:submit:end -->` 之间的区块。
  首次创建时标题取任务分支最后一个非合并提交的标题，之后不改标题。
- 提交状态写成签名记录，新增记录类型 `submit`，按 H 索引，分“已推送”和“MR 已就绪”两个阶段，重试时据此跳过已完成的步骤。
  账本写入失败会被忽略（`src/lib/store.mjs` 的 `appendLedger`），不能用作重试依据。
- 对外保证写成：某个时刻，H 相对 B 通过了本机门禁。
  不保证平台最终合入的内容，也不保证此后别人推到这个分支的提交。

### 同步：sync

- 取得 B 后要求 C 是 B 的祖先，用 C 上的配置判断 C 到 B 之间的门禁改动。
- 有门禁改动、`delivery` 变化或处于首次接入时，要求有绑定 B 的 tree 的确认记录。
  人运行 `harness confirm --branch <远程>/<主分支>` 查看并确认；现有命令已经按快进结果计算 tree，不需要新的确认方式。
- B 锁定的 harness 版本本机没有安装时，在更新主分支之前拒绝。
- 与 `merge` 共用合并锁、主 Worktree 就绪检查、令牌写入和文件同步回退；更新后刷新本机安装，执行 `postMergeCommand`。
- 普通代码改动按“信任平台主分支”导入，不在本机重新验证和评审。
- 本地模式同样可用，替代由人用绕过开关快进。

### 首次接入

- 接入分支可以 `submit`，但要先有首次接入的人工确认，接入分支提议的配置在确认之前拿不到推送权限。
- 平台合入后用 `sync` 导入，本地主分支从此成为信任根。

## 失败时

- 见验收清单的“失败时”。
- 每个拒绝都给出错误码和下一步。
  更新本地主分支之前失败的，本地主分支、主 Worktree 和远程都保持原样。

## 这次不做

- `command` 方式接入团队自己的脚本，放到 M2，届时定义稳定的输入输出协议。
- 平台压缩合并、变基合并后的 Worktree 清理，放到 M2。
  M1 里这类分支不会被 `worktree clean` 认成已合并，保守保留。
- `status` 实时查询平台上 MR/PR 的状态，M1 只显示本机提交记录和记录时间。
- fork 工作流，源与目标必须是同一个远程仓库。
- `metrics` 与 `conformance` 统计提交和同步次数。
- 平台侧的强制保护，例如受保护分支、必需审批、CI 校验门禁记录，由团队在平台上配置；harness 的本机签名其他人和 CI 无法校验。
