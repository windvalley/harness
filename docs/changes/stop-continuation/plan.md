# 收尾检查续跑：三项改动方案

- 验收清单：`docs/changes/stop-continuation/acceptance.md`

## 背景

在一个使用 harness 的项目里，同一份多阶段方案连续出现两次会话中断。

1. 第一次：某任务分支合并并推送后，会话结束。
   方案还有后续阶段，但没有任何分支处于待交付状态，收尾检查放行。
2. 第二次：后续阶段的分支已建好并授权，会话在阶段中途连续几轮只写文字汇报、没有调用工具。
   收尾检查每次提示的下一步都是 `harness verify`，而验收明显未做完，模型有理由不执行。
   两次结束之间指纹没变，收尾检查按防困住机制放行并记 `stop.unresolved`，会话停下。

## 通用性约束

- 不出现任何具体项目、阶段名或分支名，所有行为由规则与配置驱动。
- 三项改动默认行为尽量保持现状，新增配置缺省时与当前版本一致，已接入项目升级后不变。
- 不新增依赖，不新增运行时服务，不在 Stop 钩子里自动建分支、自动 `approve` 或自动合并。
- 授权不能自动继承：`approve` 的 `--note` 仍必须照录用户原话。
- 只读取已有文件与账本，不解析客户端会话记录。

## 改动一：欠项提示不再误导

问题：欠项是“缺验证、缺评审”，但分支验收明显没做完时，提示只给 `harness verify`，与模型的合理判断冲突。

做法：

- 在 `formatStopReason` 的固定说明里增加两句通用文字。
  “如果验收清单还有条目没有实现，先继续实现，每一轮必须以工具调用推进，不要只用文字汇报计划就结束。”
  “需要人决定时按上报规则处理。”
- 不解析验收清单格式，不判断完成度，避免对各项目清单写法做假设。
- 同步更新 `assets/rules/harness.md` 的“收尾检查”一节。

## 改动二：放行时让人看见

问题：无进展放行只写一条 `stop.unresolved`，人要运行 `status` 才知道。

做法：

- 放行的同时通过 Stop 钩子输出的 `systemMessage` 向用户提示：哪个分支、还欠什么、已连续几次提示无进展。
  `cmdStopHook` 已有 `notice` 通道，复用即可。
- 新增可选配置 `stop.idleBlocks`，表示指纹不变时允许再提示的次数，缺省 1，等于当前行为。
  项目可调大，给“只写汇报”的会话更多机会。
- 会话状态里记录连续无进展次数，进展出现时清零。

## 改动三：方案级后续阶段提示（默认关闭）

问题：任务分支合并后，所属方案还有后续阶段，没有机制提醒。

做法：

- 约定一份可选的机器可读文件 `docs/changes/<任务>/stages.json`，字段为阶段名、分支名、验收清单路径、顺序。
  文件名与目录由 `stop.stages` 配置给出，缺省不启用。
- 收尾检查发现本会话合并的分支出现在某份 stages 文件里，且存在顺序靠后、分支尚未创建的阶段时，生成一条提示型欠项。
  提示内容是：下一阶段名称、建议分支名、验收清单路径。
- 是否可直接 `approve` 取决于方案文字里是否有“授权覆盖全部阶段”，harness 不判断，只提示 Agent 去核对方案并按授权规则处理。
  没有授权依据时提示改为停下说明，等用户同意。
- 沿用指纹放行机制，不会把会话困住。

## 暂缓与风险

- 不做自动建分支或自动授权，理由见通用性约束。
- 改动三的 stages 文件格式是新增契约，先只支持最小字段，实践后再扩展。
- 改动一与二会让收尾提示文字变化，需要更新现有测试里依赖原文的断言。

## 实施顺序

1. 改动一：文案与规则文档，补测试。
2. 改动二：会话状态、配置与 `systemMessage`，补测试。
3. 改动三：配置与 stages 读取，补测试与文档站说明。
4. `npm test`、`npm run docs:build`、`npm run docs:check`。
5. 独立评审，按仓库规则合并到本地 `main` 并推送。
6. 不发版，发版另行授权。
