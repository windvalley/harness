# 收尾检查续跑修复

- 验收清单：`docs/changes/stop-continuation/acceptance.md`
- 关联方案：多阶段授权见 `docs/changes/stage-authorization/plan.md`，在本方案合并后单独实施。
- 任务分级：先方案后实施。
  理由是改变收尾检查的缺省行为，并修改所有接入项目都会刷新的托管块。

## 问题

在一个接入 harness 的项目里，已授权的任务分支实施到一半时，会话两次停下。
两次的过程相同：模型以文字汇报进度结束一轮，收尾检查拦下并提示下一步 `harness verify`。
验收明显没做完，模型有理由不照做，于是又以文字结束。
两次结束之间指纹不变，收尾检查只多拦一次就放行，账本记 `stop.unresolved`，用户不知道会话为什么停了。
多次停下之前，客户端都注入过“简述在做什么，然后继续”的进度提醒。
二者在时间上相关，不能证明因果。

## 根因

1. 收尾提示只按门禁状态给下一步，不区分“还在实施”与“可以验证”。
2. 无进展放行的阈值固定为一次，只读探索与文字汇报都不改变指纹，放行时也不通知用户。
3. 规则没有要求回应进度提醒后继续调用工具，文字收尾成为高频行为。

模型以文字结束一轮是模型与客户端的行为，harness 不能把会话困死，最终必须放行。
因此本方案在 harness 这一层只能降低提前停下的概率，并保证停下可见、可恢复，不能消除问题。

## 目标与非目标

目标：

- 降低实施中途提前停下的概率。
- 最终停下时，用户立即看到原因，发送“继续”即可恢复。

非目标：

- 不宣称消除文字收尾，`stop.idleBlocks` 的取值不作为根因已修复的证据。
- 不解析客户端会话记录，不解析验收清单的条目格式，不控制客户端注入的提醒。
- 不改变欠项判定、上报绑定与合并后义务的现有逻辑。

## 设计

### 一、提示按进度措辞

- 欠项是缺验证或缺评审时，下一步写明：验收清单还有未实现的条目时，先继续实现并提交，实现完成后再运行 `harness verify`。
- 固定说明增加一句：每一轮以工具调用推进；回应客户端的进度提醒后继续调用工具，不要只用文字汇报就结束。
- harness 不判断验收完成度，由 Agent 按清单自行判断。

### 二、无进展计数与阈值

- 会话状态在 `lastBlock` 里记录同一指纹的拦截次数，指纹变化时清零。
- 同一指纹的拦截次数达到 `.harness/config.json` 的 `stop.idleBlocks` 后，下一次结束放行。
- `stop.idleBlocks` 为正整数，缺省 3；取 1 时与当前版本行为一致。
- 配置值不是正整数时按缺省值处理，并在放行提示里注明已回退。
- 账本 `stop.unresolved` 增加连续拦截次数字段。

### 三、放行通知

- 放行时，`cmdStopHook` 输出 `systemMessage`，写明分支、欠项、连续拦截次数，以及发送“继续”即可恢复。
- `systemMessage` 已用于收尾检查出错的提示，Claude Code 下可显示；Codex 下是否显示在实施时实测并记录。

### 四、规则与托管块

- `src/install/managed.mjs` 托管块“已授权的任务连续推进到交付”一条补充第一节的那句要求。
- `assets/rules/harness.md` 的“收尾检查”一节说明按进度措辞、`stop.idleBlocks` 与放行通知。
- 文档站 `docs/content/principles.html` 的收尾检查说明与图 6 文案同步，运行 `npm run docs:build` 刷新生成文件。

## 兼容性

有变化的行为：

- 欠项为缺验证或缺评审时的提示文案，以及收尾提示的固定说明。
- 同一指纹的拦截次数从 1 次变为 3 次。
- 放行时多输出一条 `systemMessage`。
- 账本 `stop.unresolved` 多一个字段。
- 托管块多一句话，随项目下次刷新托管块生效。

不变的行为：

- 欠项判定，以及无欠项、要等人、已上报时的放行。
- `approve`、`status`、`merge`、`submit` 的行为与输出，`status` 对未上报结束的现有展示。
- 不新增依赖，不新增服务，方案、规则与代码不出现具体项目名。

## 已知限制

- 只读探索的轮次不算进展，模型持续以文字收尾时，拦截 3 次后仍会放行。
- 没有 Stop 钩子的客户端只获得规则文字。
- 放行通知只在同一状态第一次放行时输出；用户发送“继续”后，Agent 若仍没有产生进展就结束，不再拦也不再提示。
- DeepSeek Harness 的插件只读取拦截结果，不显示放行通知，只能在 `harness status` 里看到。
- 用户在本轮明确要求暂停时，收尾检查不读会话内容，仍会拦满 3 次，Agent 每次都要照录用户原话说明。
- 会话文件的读改写没有锁，子代理与主会话并发时可能多拦或少拦一次，这是原有问题，本次没有加重。
- `stop.idleBlocks` 没有设上限，调到很大时相当于把会话困住；修改配置属于门禁改动，需要人确认。

## 决定记录

- 拆成两次交付，本方案只覆盖收尾检查续跑，多阶段授权单独实施。
- `stop.idleBlocks` 缺省值取 3，用户原话：“按你的顺序修改方案，失效范围用细分版，缺省值取 3”。
