# 收尾检查续跑与多阶段方案

- 验收清单：`docs/changes/stop-continuation/acceptance.md`
- 任务分级：先方案后实施。
  理由是新增方案格式与授权方式，改动跨 `plan`、`stop`、`status`、`install` 与规则文档多个模块。

## 问题

超大需求的 spec 与 plan 定稿后，一个任务分支只能完成其中一部分，需要多个分支依次交付。
在一个接入 harness 的项目里，这类需求先后出现三次会话中断。

1. 某个分支合并并推送后，会话结束。
   方案还有后续阶段，但本会话没有未交付的分支，收尾检查放行。
2. 后续阶段的分支已建好并授权，实施到一半时，模型连续几轮只写文字汇报就结束。
   收尾检查每次提示的下一步都是 `harness verify`，而验收明显没做完，模型有理由不照做。
   两次结束之间指纹不变，只多拦一次就放行，账本记 `stop.unresolved`，用户不知道会话为什么停了。
3. 中途合入的分支命名规则让原定的阶段分支名失效，Agent 改名后只能重新记录授权并复制验收清单，随后再次按第 2 条的方式停下。

会话记录显示，多次停下之前客户端都注入过“简述在做什么，然后继续”的进度提醒，模型汇报后直接结束了这一轮。
二者在时间上相关，不能证明因果，但说明文字汇报收尾是高频行为。

## 根因

1. 收尾检查的单位是分支，不是需求；多阶段方案在阶段之间没有任何待办记录。
2. 收尾提示只按门禁状态给下一步，不区分“还在实施”与“可以验证”。
3. 无进展放行的阈值固定为一次，只读探索与文字汇报都不改变指纹，放行时也不通知用户。
4. 规则没有要求每一轮以工具调用推进，客户端的进度提醒会放大文字收尾。
5. 授权绑定在分支名上，分支改名就要重新授权。

## 目标与非目标

目标：

- 多阶段方案在用户一次授权覆盖全部阶段时，阶段之间不再断开。
- 实施中的分支不因提示与进度错位而停下。
- 会话确实停下时，用户能立即看到原因与恢复方式。

非目标：

- 不在 Stop 钩子里自动建分支、自动授权或自动合并。
- 不解析客户端会话记录，不解析各项目验收清单的条目格式。
- 不控制客户端注入的提醒。
- 不改变验收清单按分支名定位的约定。

## 设计

### 一、多阶段方案与阶段授权

- 方案目录里可选放一个阶段文件，默认路径模式 `docs/changes/*/stages.json`，可由 `intent.plan.stages` 覆盖。
  没有阶段文件时，本节的所有逻辑都不执行。
- 阶段文件按顺序列出阶段，每项包含 `id`、`title`、建议分支名 `branch` 与阶段验收清单路径 `acceptance`。
- `harness approve --branch <分支> --note "<用户原话>" --stages <阶段文件> [--stage <id>]` 记录一份覆盖全部阶段的授权。
  记录内容包括用户原话、阶段文件哈希、每个阶段验收清单的哈希，以及当前分支对应的阶段（缺省为第一个阶段）。
  命令会校验阶段 `id` 唯一、阶段验收清单已在分支上提交、建议分支名符合当前 `branch-name` 规则。
- `harness approve --branch <新分支> --from-stages <阶段文件> --stage <id>` 为后续阶段记录授权。
  它不接受 `--note`，原话直接取自阶段授权记录，并在普通授权记录里写明来源，现有门禁读到的仍是普通授权记录。
  它会拒绝以下情况：主分支上的阶段文件与授权时不一致、新分支的验收清单与该阶段授权时的哈希不一致、前序阶段尚未合入主分支。
- 阶段与分支按阶段 `id` 关联，不按分支名关联。
  分支因命名规则改名后，用合规的新名字运行 `--from-stages` 即可，不需要用户重新授权。
- 收尾检查在本会话推进过的分支已合入、且它对应某个阶段授权时，查找下一个未合入的阶段。
  下一阶段还没有分支时，生成欠项，下一步写明建议分支名、要复制的阶段验收清单和 `approve --from-stages` 命令。
  下一阶段已有分支但还没交付时，提示接着完成那条分支。
  全部阶段合入后不再提示。
- 不带 `--stages` 的授权与现在完全一致。
- `harness status` 对阶段分支多显示一行方案进度：已合入阶段数、总数与下一阶段。

### 二、收尾提示按进度给下一步

- 欠项是缺验证或缺评审时，提示同时写明：验收清单还有未实现的条目时，下一步是继续实现并提交，实现完成后再运行 `harness verify`。
- 固定说明增加一句：这一轮必须以工具调用推进，不要只用文字汇报计划就结束。
- harness 不判断验收完成度，由 Agent 按清单自行判断。

### 三、无进展放行可配置并通知用户

- 会话状态记录指纹不变的连续次数，进展出现时清零。
- 连续次数超过 `.harness/config.json` 的 `stop.idleBlocks` 才放行，缺省 3。
  当前版本相当于 1，这是一处有意的行为变化，只会让会话多被拦几次，不会多拦交付。
- 配置值不是非负整数时回退缺省值，并在放行提示里注明。
- 放行时通过 Stop 钩子的 `systemMessage` 告诉用户：哪个分支、还欠什么、连续几次没有进展、发送“继续”即可恢复。
- 账本的 `stop.unresolved` 增加连续次数字段。

### 四、规则与托管块

- `src/install/managed.mjs` 托管块“已授权的任务连续推进到交付”一条补一句：
  每一轮以工具调用推进，进度汇报只夹在工具调用之间；客户端要求简短汇报时，汇报后继续调用工具，不结束这一轮。
- `assets/rules/harness.md` 的“收尾检查”与“实施授权”两节同步更新，写明阶段文件与两种 `approve` 用法。
- `assets/rules/method-design-planning.md` 补充：预计一个分支交付不完的需求，按阶段拆分并写阶段文件。
- 文档站 `docs/content/principles.html` 的收尾检查说明与图 6 文案同步，运行 `npm run docs:build` 刷新生成文件。

## 通用性与兼容性

- 方案、规则与代码里不出现任何具体项目、阶段名或分支名。
- 没有阶段文件的项目只感受到两处变化：收尾提示文案，以及无进展放行从 1 次变为 3 次。
- 托管块文字的变化随项目下次刷新托管块生效，沿用现有升级路径。
- 没有 Stop 钩子的客户端只获得规则文字与 `status` 的方案进度。
- 不新增依赖，不新增服务。

## 授权边界

- 用户原话只能来自用户；`--from-stages` 只复用已记录的原话，不接受新原话。
- 阶段文件或任何阶段验收清单改动后，原阶段授权失效，必须向用户说明并重新授权。
- 前序阶段未合入时拒绝为后续阶段记录授权。
- 授权是否覆盖全部阶段由用户决定，Agent 只有在用户明确同意覆盖全部阶段时才可以使用 `--stages`。

## 已知限制

- 验收清单仍按分支名定位，阶段分支改名后要把阶段验收清单复制到新路径，内容不变即可通过校验。
- 只读探索的轮次仍不算进展，`stop.idleBlocks` 只能降低而不能消除提前放行。
- 远程交付由平台 squash 或 rebase 合入时，判断阶段已合入沿用义务记录的祖先判断限制，需要 `harness sync` 后才能识别。
