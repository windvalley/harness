# 收尾检查续跑修复验收

## 范围

收尾提示按进度措辞、同一指纹拦截次数可配置、放行时通知用户、规则与托管块补充。
不解析客户端会话记录与验收清单条目，不改变欠项判定，不出现项目专属名称。
本方案只降低提前停下的概率并保证停下可见，不宣称消除文字收尾。

## 提示

- 欠项为缺验证或缺评审时，提示写明验收未完成时先继续实现并提交，实现完成后再运行 `harness verify`。
- 收尾提示的固定说明要求每一轮以工具调用推进，回应进度提醒后继续调用工具。
- 提示与规则不硬编码具体项目或示例名称，动态展示的实际分支名除外。

## 无进展拦截

- 未配置 `stop.idleBlocks` 时，同一指纹最多拦截 3 次，之后的结束放行。
- 配置为正整数 N 时，同一指纹最多拦截 N 次；N 为 1 时，拦截与放行的时机和当前版本一致。
- 指纹变化后拦截次数清零，重新计数。
- 配置值不是正整数（包括 `stop` 不是对象）时按 3 处理，放行提示注明已回退，收尾检查不报错。
- 旧版或损坏的会话记录缺少有效拦截次数时，按已拦截一次计数。

## 放行通知

- 放行时输出 `systemMessage`，包含分支、欠项、连续拦截次数和“发送继续即可恢复”。
- 账本 `stop.unresolved` 记录连续拦截次数。
- 在 Codex 下实测放行通知是否显示，结果写入验证记录；不显示时说明影响。

## 兼容性

- 有变化的只有：缺验证或缺评审时的提示文案与固定说明、同一指纹的拦截次数、放行时的 `systemMessage`、`stop.unresolved` 新字段、托管块新增的一句。
- 无欠项、要等人与已上报时的放行行为和输出与当前版本一致。
- 欠项判定与其他欠项的下一步命令与当前版本一致。
- `approve`、`status`、`merge`、`submit` 的行为与输出不变，`status` 对未上报结束的展示不变。

## 规则与文档

- 托管块包含新增要求，托管块测试同步更新。
- `assets/rules/harness.md` 的“收尾检查”一节与文档站说明、图 6 文案同步，`npm run docs:build` 的生成差异经过审查。
