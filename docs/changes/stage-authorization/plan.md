# 多阶段方案授权与阶段续跑

- 验收清单：`docs/changes/stage-authorization/acceptance.md`
- 前置：`docs/changes/stop-continuation/plan.md` 合并后实施，复用其中的提示措辞与放行通知。
- 任务分级：先方案后实施。
  理由是新增方案格式与授权方式，改动跨 `plan`、`stop`、`status` 与规则文档多个模块。

## 问题

超大需求的 spec 与 plan 定稿后，一个任务分支只能完成其中一部分，需要多个分支依次交付。
在一个接入 harness 的项目里，用户一次授权覆盖了全部阶段，但出现了两个问题。

1. 某个阶段分支合并并推送后，会话结束。
   方案还有后续阶段，但本会话没有未交付的分支，收尾检查放行。
2. 实施中途合入的分支命名规则让原定的阶段分支名失效。
   Agent 改名后，只能重新记录授权并复制验收清单。

## 根因

1. 收尾检查的单位是分支，不是需求，阶段之间没有任何待办记录。
2. 授权绑定在分支名上，分支改名就要重新授权。

## 目标与非目标

目标：

- 用户一次授权覆盖全部阶段时，一个阶段合并后，收尾检查要求 Agent 开始下一阶段。
- 阶段分支因命名规则改名时，不需要用户重新授权。
- 方案材料在授权后变化时，受影响的授权在所有门禁入口一致失效。

非目标：

- 不自动建分支、自动授权或自动合并。
- 不改变验收清单按分支名定位的约定。
- 没有阶段文件的项目，`approve`、`status`、`merge` 与收尾检查的阶段逻辑都不执行。

## 设计

### 一、阶段文件

- 方案目录里可选放一个阶段文件，默认路径模式 `docs/changes/*/stages.json`，可由 `intent.plan.stages` 覆盖。
- 阶段文件按顺序列出阶段，每项包含 `id`、`title`、建议分支名 `branch` 与阶段验收清单路径 `acceptance`。

### 二、授权命令

- `harness approve --branch <分支> --note "<用户原话>" --stages <阶段文件> [--stage <id>]` 记录覆盖全部阶段的方案级授权。
  记录按阶段文件路径做键，同一份方案只有一条当前记录，重新授权时覆盖。
  记录包含用户原话、阶段文件哈希、每个阶段验收清单的哈希、授权时间、携带分支，以及携带分支对应的阶段（缺省为第一个阶段）。
  每次授权都在账本追加 `plan.approve` 事件，历次原话与哈希可以从账本追溯，不另存历史记录。
  命令校验阶段 `id` 唯一、阶段文件与全部阶段验收清单已在分支上提交。
- 建议分支名不符合当前 `branch-name` 规则时，命令只给出提示，不拒绝。
  授权之后才合入的命名规则无法在这里预防，改名问题由按 `id` 关联解决。
- `harness approve --branch <新分支> --from-stages <阶段文件> --stage <id>` 为后续阶段记录派生授权。
  它不接受 `--note`，原话取自方案级授权记录，并在普通授权记录里写明阶段文件路径与阶段 `id`。
  它在以下情况拒绝：主分支上的阶段文件与方案级记录不一致、新分支验收清单与该阶段记录的哈希不一致、前序阶段尚未合入主分支。
- 阶段与分支按阶段 `id` 关联，分支改用合规的新名字后运行 `--from-stages` 即可。

### 三、授权的运行时校验（细分版）

校验放在 `approvalState` 里。
`status`、`merge`、`review` 与收尾检查都调用它，实施时核对 `submit` 的授权判定路径并纳入同一校验。

- 来源记录的查找规则唯一：按派生记录里的阶段文件路径取当前的方案级授权记录。
- 携带方案级授权的分支：除现有的分支名与本分支验收清单哈希外，还校验来源记录登记的携带分支就是本分支，以及本分支上的阶段文件哈希和全部阶段验收清单哈希。
  任一不一致即判为未授权，原因写明“方案材料在授权后改过，需要向用户说明并重新授权”。
  修订后的方案在别的分支重新授权后，旧携带分支随之失效。
- 派生授权的分支：除现有校验外，还校验来源记录存在且验签通过，且来源记录里本阶段的哈希等于本分支验收清单哈希。
  不校验授权时间，有效性只由内容哈希决定。
  用户重新授权修订后的方案时，只有本阶段验收清单变化的派生授权失效，其他阶段的派生授权保持有效。
  本阶段改回授权过的原内容时，派生授权恢复有效。
- 重新授权后，未改动阶段的派生记录仍显示派生时的原话；有效性由内容决定，两次原话都在账本里。
- 主分支上其他阶段的材料变化不影响已派生的分支。
  被改动的阶段在 `--from-stages` 入口因哈希不一致被拒绝，需要用户重新授权。

### 四、收尾检查与 status

- 本会话推进过的分支已合入、且它对应某个阶段授权时，收尾检查查找下一个未合入的阶段。
- 下一阶段还没有分支时生成欠项，下一步写明建议分支名、要复制的阶段验收清单与 `approve --from-stages` 命令。
- 下一阶段已有未交付分支时，提示接着完成那条分支；全部阶段合入后不再提示。
- 方案级授权或来源记录失效时，不生成续跑欠项，改为提示需要用户重新授权。
- `harness status` 对阶段分支多显示一行方案进度：已合入阶段数、总数与下一阶段。

### 五、规则与文档

- `assets/rules/harness.md` 的“实施授权”一节写明阶段文件、两种授权用法与失效规则。
- `assets/rules/method-design-planning.md` 补充：预计一个分支交付不完的需求，按阶段拆分并写阶段文件。
- 只有用户明确同意授权覆盖全部阶段时，Agent 才能使用 `--stages`。
- 文档站同步说明，运行 `npm run docs:build`。

## 授权边界

- 用户原话只能来自用户，`--from-stages` 只复用已记录的原话。
- 前序阶段未合入时拒绝派生授权。
- 收尾检查只提示下一步，不执行建分支、授权或合并。

## 已知限制

- 验收清单仍按分支名定位，阶段分支改名后要把阶段验收清单复制到新路径，内容不变即可通过校验。
- 远程交付由平台 squash 或 rebase 合入时，判断阶段已合入沿用义务记录的祖先判断限制，需要 `harness sync` 后才能识别。

## 决定记录

- 失效范围采用细分版，用户原话：“按你的顺序修改方案，失效范围用细分版，缺省值取 3”。
- 阶段信息放在独立的 `stages.json`，用户原话：“改方案文档，stages.json 独立文件接受，第一份授权实施”。
- 来源记录按阶段文件路径做键并按内容哈希判定，不引入不可变的授权 ID；理由是账本已提供只追加的审计历史，这种做法改动最小。

## 方案评审意见与处理

第一轮评审者：kimi k3.1pro，由用户运行后转达，客户端与 effort 未知。

| 意见 | 级别 | 处理 |
| --- | --- | --- |
| 阶段授权变化后，已派生授权仍可合并 | High | 采纳，校验放入 `approvalState`，按用户选定的细分版：携带方案级授权的分支校验全部材料，派生分支校验本阶段材料与来源记录 |
| 只在授权入口校验不够 | High 附带 | 采纳，见设计第三节 |
| 授权后材料变化缺少失效测试 | High 附带 | 采纳，见验收清单“授权失效” |
| 无阶段项目的兼容性验收互相矛盾 | Medium | 采纳，本方案的兼容性只约束阶段逻辑，收尾提示与阈值变化由收尾检查续跑方案约束 |

自查补充：

- 授权时校验建议分支名挡不住授权之后才合入的命名规则，改为只提示，改名问题由按 `id` 关联解决。

第二轮评审者：kimi，由用户运行后转达。

| 意见 | 级别 | 处理 |
| --- | --- | --- |
| 校验来源授权时间会让重新授权后未改阶段的派生授权一并失效，且来源记录的键与选择规则未定义 | High | 采纳评审给出的第二种修法：取消授权时间校验，来源记录按阶段文件路径做键，派生授权只按当前来源记录中本阶段的哈希判定 |
| 补充完整顺序测试 | High 附带 | 采纳，见验收清单“授权失效” |

按方案评审最多两轮的规则，本次修改后不再强制评审。
