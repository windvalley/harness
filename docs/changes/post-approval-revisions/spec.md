# 行为说明

- 验收清单：`.harness/acceptance/feature-post-approval-revisions.md`
- 实施方案：同目录的 plan.md
- 核心契约：同目录的 contract.md

## 问题

- 任务授权后进入实施，Agent 发现方案或验收清单需要调整，被门禁要求停下等人确认，任务中断。
  实践中大部分调整是正确的，而用户确认方案时往往没有逐条看全，中途确认的把关价值低于中断成本。
- 现状一：核心契约 `contract.md` 是可选文件，规则只写“复杂任务使用”。
  授权时没有契约就绑定整份验收清单（`src/plan/plan.mjs:103`），之后改任何一条都会失效，而且只能由人执行 `--confirm-contract` 恢复（`src/plan/plan.mjs:368`、`assets/presets/gate-self.json:71`）。
- 现状二：多阶段授权中，没有 `contract` 字段的阶段同样绑定整份阶段清单（`src/plan/stages.mjs:171`）。
- 现状三：核心契约模板要求写“选定的重要交互或技术方案”（`assets/templates/contract.md:7`），实现中最常见的技术调整也会触发人工确认。
- 现状四：规则自相矛盾。
  `assets/rules/method-design-planning.md:17` 说契约任务可以持续细化清单，`assets/rules/harness.md:259` 却说改清单要先取得同意。
- 现状五：授权后的修订没有统一汇报出口。
  评审把授权后改过的清单仍标为“用户已同意按它实施”（`src/review/review.mjs:716`），合并输出与 PR/MR 描述只有授权原话，没有修订内容。

## 目标行为

- 授权只绑定核心契约。
  契约只写事后纠正代价高的内容：用户目标与交付结果、用户可见交互、验收底线、必需证据、授权范围。
- 契约以外的验收清单、行为说明、实施方案，Agent 在实施中按实际情况自主修订，不停下确认。
- 修订内容由 harness 从授权时的提交机械算出，在 `status`、交接视图、合并输出、PR/MR 描述中给出；Agent 只补写理由。
  用户在交付汇报里看到改了哪些条目、为什么改，有异议再澄清。
- 独立评审代替人做机械把关：拿到契约和修订条目，判断修订有没有越过契约、删减或放宽有没有理由。
- 新任务记录授权时必须有核心契约，堵住“没写契约就整份清单绑定”这个主要中断来源。
- 旧记录保持原语义，不迁移。

## 失败时

- 基线提交无法还原时如实说明，不伪造“没有修订”，不阻断交付。
- 缺少契约时 `approve` 明确拒绝并给出模板路径，不改动已有记录。

## 这次不做

- 不改变阶段文件 `stages.json` 本身的绑定：阶段划分属于交付范围，改动仍需重新授权。
- 不迁移旧记录，不给旧记录自动补契约。
- 不改变直接实施小任务的流程，它们本来不需要授权。
- 不新增 CLI 子命令或参数；修订摘要复用现有 `status`、`merge`、`submit` 输出。
- `plan.md` 只给章节级变化与理由，不给逐条原文 diff：执行进度更新会淹没实质修订。
- 不改变评审 verdict 的判定逻辑，只补充评审输入与说明。
