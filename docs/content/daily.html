日常工作流

规则已经写进项目（AGENTS.md 托管块与 .harness/rules/），用平常的话描述想法、问题或希望的变化即可。理解需求、澄清关键问题、整理验收标准和交付结果由 Agent 主动负责。下文的 harness 都指项目里的入口 .harness/bin/harness。

如何表达需求与后续协作

下面是两个普通需求示例，不是必须照抄的提示词模板。用户不需要预先填齐验收标准、安排工作流程或重复交付要求，实际分级由 Agent 核对仓库后判断。

大需求：先讨论，再授权实施

描述想法即可
给系统增加用户登录和权限管理功能，支持管理员创建用户、分配角色，并限制不同角色可以访问的页面和接口。

这类需求涉及认证与授权。Agent 应先了解现状，再与你讨论登录方式、角色权限和现有用户数据兼容等关键问题，主动整理验收清单、行为说明与实施方案。

关键问题已明确或由你标为待定后，Agent 应保留未决问题并说明影响，主动进入方案，不需要你宣布问题问完或指挥写文档。方案交付后它应停下，等待你明确同意实施该方案。

最初表达需求不替代方案交付后的实施授权，对某个澄清答案或方案细节的认可也不等于同意实施。授权不要求固定措辞。

小需求：核实范围后可以直接实施

描述希望的变化即可
在创建用户的表单中增加邮箱格式校验，输入不合法时显示错误提示，并阻止提交。

Agent 核实这只是现有表单的局部校验，不需要调整接口、数据结构或权限且满足小任务条件后，可以直接实施，并验证合法与不合法邮箱的提交行为。发现影响超出小任务范围时，应转入讨论、方案和授权流程。

用户当前只要求分析、评估或讨论时仍保持只读，不能因为需求看起来小就动手。用户也可以补充约束或调整节奏。

一次任务

两类任务都由 Agent 整理验收标准，关键业务含义有歧义时再与你确认，按相应流程准备任务分支及需要的 Worktree，执行验证和独立评审，再按项目的交付方式交付：本地合并，或提交 PR/MR。没过门禁时它按拒绝原因修复后重跑；改动涉及门禁本身时由你亲自确认，同一个问题连续三轮修不好时停下说明。用户不需要额外提醒它汇报效果入口、验收结果和最终交付状态。

  • 看阶段：大需求先讨论并交付方案，明确授权后才实施；小需求核实范围后可以直接实施。
  • 看效果：从约定入口查看已经实施的结果；例如小需求中非法邮箱会提示错误并阻止提交，合法邮箱仍可正常提交。
  • 看证据：验收逐条对应需求，验证与独立评审有结果，未执行项与阻塞明确列出。
  • 看状态：本地交付说明已合并、待你同意合并还是被阻塞；远程交付说明已提交 PR/MR 等平台合并、平台已合入并已同步还是被阻塞。同时给出分支、提交与工作区位置。

Agent 可以通过 status 汇总还差什么。下面示例表示门禁条件已满足，但没有验收清单，需求符合度仍是 unknown，不能据此宣布用户需求已经验收通过：

分支 feat/login -> main

  [ok] branch: 待合入 5685e8a474 -> main
  [ok] main-worktree: 主 Worktree 停在 main 且洁净
  [ok] evidence: 验证通过，主分支自验证以来新增 0 个文件，未波及已执行的检查，可直接复用
  [ok] review: 评审通过（需求符合度 unknown，工程质量 good，清单来源 无）
  [ok] plan: 属于直接实施的范围（代码改动 1 行），不需要实施授权
  [ok] gate: 本次没有改动门禁配置与规则
  [-] acceptance: 验收清单约定位置：acceptance/feat-login.md（存在时评审会核对需求符合度）

可以合并：harness merge --branch feat/login
  • 合并前的工作区检查、常规冲突处理和重新验证由 Agent 按项目规则执行。
  • 涉及用户已有改动或业务意图无法判断时，Agent 说明具体分歧，交由你决定。

执行命令与合并条件见一次任务参考。

验证入口受阻时

遇到台账、依赖或命令启动问题时，Agent 先确认必要验收、失败阶段和存量证据，再核对是否有项目允许的等价定向入口。 入口失败不等于目标行为失败；真实页面的定向浏览器验收可以证明受影响交互，但页面加载、静态检查或单元测试不能代替未覆盖的交互。

有合规恢复路径就继续执行，必需 gate 仍须通过，合并前 extended 仍为可选项并如实披露。 不默认跑全量基线、不扩修无关问题；必要验收仍不可行且需要人决定时才上报。 每项结果的 reasonCode 与 blockedBy 帮助区分本项失败和前置失败导致的未执行，普通非零退出不能自动归为环境或断言问题。

已经上报的技术阻塞消除后，用 escalate resolve --id <编号> --reason <原因> --evidence <引用> 留下原因与证据并继续交付。 这不冒充用户答复，也不免除验证、评审与人工确认；详细诊断与命令见被拦截时怎么办。

验收清单

清单放在 .harness/acceptance/<分支名>.md，分支名里的 / 等字符换成 -，例如 feat/login 对应 feat-login.md。每条写成能用测试或命令验证的结果。没有清单时评审只评工程质量；intent.mode 设为 required 时没有清单不能合并。

默认都是合并前验收。确实需要目标分支集成状态时，把条目写进“合并后验收”章节，并配置对应的 post-merge 检查；只写章节却没有对应检查时，验证会明确失败，不会让这条义务悄悄漏掉。

提交信息

提交信息规范只在 .harness/policy.json 的 commit-message 规则里定义一处，commit-msg 钩子、verify 与 review 的前置检查、status 和合并共用同一份判定。可以直接约定描述用什么语言（lang 取 zh、en 或 any）、允许的类型、标题长度与正文格式。

git commit -m "feat(login): 支持短信验证码登录" -m "- 新增验证码发送与校验接口
- 登录页增加验证码输入"

每个 -m 是一段，多条要点要写在同一个 -m 里换行，或者用编辑器写。不合规时提交当场被拒，并列出违反的条目与示例；已经提交的要改写提交信息，再重新 verify、review。

清理任务 Worktree

合并后保留任务 Worktree 和分支，因为会话可能还停在里面。需要清理时向 Agent 发起请求：

清理需求示例
我想清理已经完成的任务工作区。

Agent 应先给出预览，列出具体目录、分支、会连带删除的本机文件和跳过原因，不立即删除。看过预览并明确确认具体对象后再清理；含本机文件的目录需要单独明确同意，主 Worktree、命令所在 Worktree 和验证检出会保留。

预览还会检查提交是否已合并、新任务保护、未提交文件、进程和锁定情况。详细条件和命令见清理参考。
