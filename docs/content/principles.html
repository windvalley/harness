核心原理

一次任务的生命周期

每一步都会留下一条签名记录，并且绑定到具体的内容上。自动检查与独立评审绑定分支提交；外部证据绑定检查定义和它覆盖的文件；合并后证据绑定实际集成结果。相关内容变化后旧证据失效，无关文档变化则不必重验。这样核对的永远是“这一份代码”的证据，而不是“某个时候跑过一次”。

  • verify 在固定检出里检出分支提交，只验证已提交的内容；工作区里没提交的改动不算。
  • review 要求先有通过的验证证据，评审结论同样绑定分支提交。
  • confirm 只在改动涉及门禁本身（配置、规则、入口、钩子）时需要，绑定的是合并结果的 tree。
  • merge 发现没有证据、主分支的新改动波及某些检查，或检查配置变了时，会自己重跑需要的检查；评审不会自动重做，主分支在评审之后改了本分支也改过的文件时评审作废。

签名记录

证据、评审、确认与实施授权都是 JSON 记录，用本机密钥 ~/.local/share/harness/evidence.key（权限 600）做 HMAC-SHA256 签名，存在仓库的 .git/harness/ 下，所有 Worktree 共用，另有一份追加式账本 ledger.jsonl。

记录被改动、密钥轮换或丢失时，签名校验失败，harness 会指出该重跑哪一步（例如 harness verify --branch <分支>），而不只是报“签名不匹配”。

主分支只认合并令牌

主分支的保护不靠“约定不要直接提交”，而是由 git 自己的 reference-transaction 钩子执行：每次更新 refs/heads/main 时，钩子都要求环境里带着合并令牌。

所以在主分支上 git commit 或 git pull 被拒绝是预期行为。同步远端主分支的做法见 团队与多机。

配置只从主分支读取

如果任务分支能改规则并立即生效，Agent 就可以“先关掉检查再提交”。harness 的所有判定（实时拦截、git 钩子、verify 选检查、merge 的合并条件）都从主分支的 git 对象读取配置，不读工作区，也不读任务分支。

  • 门禁文件包括 .harness/ 下的配置、规则、用例与入口，客户端配置和钩子目录，以及 governance.gatePaths 追加的路径。
  • Agent 执行带 --yes 的确认会被拦截，确认必须由人执行；确认后如果分支再提交或主分支前进导致合并结果变化，要重新确认。
  • 首次接入时主分支上还没有配置，这时按接入分支提议的配置执行，并且无论改了什么都要人确认；确认后以快进方式合入，这份配置从此成为信任根。
  • 改规则之前可以用 harness golden --worktree 按工作区的配置重放黄金任务，确认新规则的判定符合预期。

按改动选检查

verify 不是每次全量跑测试，而是按 .harness/verify.json 的映射，用“分支相对合并基线改了哪些路径”选出要跑的检查：

verify.json 片段
{ "id": "web-typecheck", "tier": "gate",
  "when": ["web/src/**", "web/package.json"],
  "cwd": "web", "cmd": ["pnpm", "typecheck"],
  "requires": ["web/node_modules"] }
tier含义
gate必过，失败就不能合并
extended在外部环境执行；成功后用 attest 登记为正式证据，未登记时明确列为未执行
advisory只提示，不计入未执行
  • 检查在固定检出 ~/.cache/harness/checkouts/<哈希>/work 里执行，它是一个分离头指针的 Linked Worktree，不受你工作区状态影响，增量缓存可以复用。
  • requires 里的依赖目录（如 node_modules）从主 Worktree 软链接进检出；缺失时证据记为 incomplete，不能评审与合并。
  • 命令不存在时证据里单独标出“未找到命令”，说明是缺工具，不是代码有问题。
  • harness verify --plan --branch <分支> 只列出会执行的检查，不执行；配置了 testFirst、coverage 时，这次会复算的也一并列出。

外部验证与合并后验收

有些检查需要真实浏览器、登录态或已经集成的环境，不适合由 verify 在固定检出里直接运行。harness 把这类情况分成“外部验证”和“合并后验收”，既不把没跑说成通过，也不要求在合并前提供只有合并后才能取得的证据。

自动检查

gate 仍由 verify 自动运行，失败就不能交付，流程不变。

外部验证

Agent 或你在真实环境执行 extended 检查，成功后用 attest 登记实际命令和报告，不需要把报告提交进仓库。

合并后验收

只有必须等代码进入主分支才能验证的项目才标为 post-merge，例如主 Worktree 集成冒烟测试；能在任务 Worktree 验证的仍在合并前完成。

外部检查已成功执行后登记
harness attest --branch feat/login --check browser \
  --command "pnpm ui:verify" \
  --report frontend/output/report.md
  • 不是再跑一遍：attest 只登记已经成功的验证。证据包含实际命令、报告哈希和脱敏摘要，评审可以据此核对，而不是只看 Agent 自述。
  • 无关改动不重验：只改文档时外部证据继续有效；检查定义或覆盖文件变化后，旧证据自动失效。
  • 两种交付都一样：本地项目在 merge 后验收；PR/MR 项目在平台合入并 sync 后验收。没有配置合并后检查的项目不增加任何步骤。
  • 发现问题继续修：验收失败会保持待完成，Agent 新建修复分支并重新走门禁；需要回滚、业务取舍或其他用户决策时，才上报并等待。
  • 注意脱敏：报告摘要会提供给评审者；原始命令不会写进 PR/MR 描述，平台只看到检查名和报告哈希。

从配置、验收清单到合并、登记和失败修复的完整命令与输出，见参考手册里的合并后验收示例。

测试证据：先红后绿与改动行覆盖率

“检查通过”证明不了“测试真的约束了这次改动”。verify.json 里两个可选字段补上这一环，由验证自己复算，不靠 Agent 自述：

verify.json 片段
"testFirst": {
  "mode": "observe",
  "source": { "match": ["web/src/**"], "exclude": [] },
  "tests":  { "match": ["**/*.test.ts"], "exclude": [] },
  "cwd": "web", "cmd": ["pnpm", "exec", "vitest", "run", "{tests}"]
},
"coverage": {
  "mode": "observe",
  "include": { "match": ["web/src/**"], "exclude": [] },
  "cwd": "web", "cmd": ["pnpm", "exec", "vitest", "run", "--coverage"],
  "report": "coverage/lcov.info", "threshold": 80
}
  • testFirst：改了实现就必须有新增或修改的测试；这些测试在当前实现上要通过，把实现还原成基线后要失败，才算测试先于实现红过。行为不变的重构在提交信息里写 Tdd-Waiver: 原因，只留痕，不是人工放行。
  • coverage：只统计 git diff 里新增或修改的行，读 lcov 或 Go coverprofile，低于 threshold（默认 80）失败并列出没覆盖的行。
  • mode 先写 observe（只记录不拦截），在真实改动上看过误报再改 enforce。
  • 两项在证据里记为 harness:tdd-red 与 harness:changed-line-coverage；它们只证明“有测试会红、改动行被执行过”，不证明断言有效。调低阈值或改成 observe 属于门禁改动，确认摘要会列出改前改后。
  • init 不会自动生成这两项，接入时由 Agent 按项目真实的测试与覆盖率工具配置。

独立评审

写代码的 Agent 很难客观评价自己的改动。review 启动一个不了解实现过程的评审进程，只给它评审材料：验收清单、验证证据摘要、提交说明、改动文件统计和 diff，从“需求符合度”和“工程质量”两个维度给出结论。

  • 评审者在本机配置（harness reviewer，文件是 ~/.config/harness/reviewers.json，不进仓库）：每个评审者指定客户端（claude、codex 或任意命令）、模型、推理强度，claude 还可以指定第三方端点和 key。换模型不需要提交，也不触发门禁确认。
  • 可以列多个评审者：前一个失败（鉴权、限流、超时）就换下一个，给出结论就停，被拒后不会换人重评。默认优先使用与当前会话模型不同的评审者，评审和实现不共用同一套盲点。
  • 没有本机文件时按项目配置里的旧字段运行：本机有 claude 就用它，否则用 codex。
  • claude 不开放任何工具、不加载项目设置；codex 与 command 在空的临时目录里运行，读不到项目文件。
  • 评审记录写明由谁、用什么模型、什么端点完成，harness status 与 PR/MR 描述里都能看到。
  • 有 high 或 critical 级别的发现时拒绝合并，级别可以用 review.blockSeverities 调整。
  • 提交说明标明是实现方自述，只用来理解意图；说法与 diff 不符时，评审会作为发现报出来。
  • diff 超过 review.maxDiffChars（默认 300000 字符）时拒绝评审，并按目录给出拆分建议。
  • 有验收清单 .harness/acceptance/<分支名>.md 时评审逐条核对，需求符合度为 unknown 或 unmet 都会被拒绝。

任务分级与实施授权

规则写在 .harness/rules/core.md，要点同时写进 AGENTS.md 的托管块，Agent 开始任务前先判断分级：

直接实施

小优化、小迭代或缺陷修复：不改库表与迁移，不改接口契约、权限与数据兼容性，代码改动少于 500 行（测试、文档、锁文件不计）。

先方案后实施

其余任务和拿不准的任务：先探索仓库，一次问一个问题，写出验收清单、spec 与 plan，提交后停下等你授权。配置了评审者时，交出方案前先运行 harness review-plan 让另一个模型审一轮，意见与处理记进 spec；它只给建议，不是门禁。

默认启用的 plan-first 预设把“停下等授权”变成门禁：

  • 任务分支写了实施方案（默认 docs/changes/*/plan.md）、还没有授权记录时，Agent 只能写方案与验收清单，写测试和代码会被拦截。
  • 你在对话里说“开始实施”之类的话就是授权，不需要执行命令。Agent 会运行 harness approve --branch <分支> --yes --note "<你的原话>" 照录原话。
  • 写了方案、改了库表相关文件或代码改动超过阈值的分支，没有授权记录不能合并（plan_unapproved）。
  • 合并输出与 harness status 会显示记录下来的原话，你可以随时核对。

实施默认先红后绿：先把每条验收写成测试并确认失败，再实现到全部通过。

版本锁定的入口

门禁代码如果放在项目里，Agent 就可以改它。所以项目只入库一个入口 .harness/bin/harness，它按 .harness/VERSION 锁定的版本，转发到本机的 ~/.local/share/harness/versions/<版本>/。

  • 版本目录带内容哈希清单，harness doctor 会校验它没有被就地改写。
  • 入口与钩子 Agent 不能手改，只能在任务分支运行 harness install、init 或 upgrade 重新生成，合并前同样要人确认。
  • 入口随仓库分发，每个 Linked Worktree 检出即可用；同一台机器上的多个项目可以锁定不同版本。
