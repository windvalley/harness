团队与多机

新成员或新机器

入口与客户端配置随仓库分发，门禁代码与 git 钩子留在各自的机器上。工具调用可用时，可以交给 Agent：

说明当前目标
我想在这台新电脑上继续开发这个项目。

Agent 应检查项目锁定的版本，完成本机安装与诊断，并说明需要用户完成的客户端操作。

本机没有安装锁定版本时，已启用的实时拦截可能拒绝所有 Agent 工具调用。此时由人在项目目录的终端先完成安装，再让 Agent 接续诊断：

工具调用被拦截时，由人执行
cd <项目>
node ~/github/harness/bin/harness.mjs install --local
.harness/bin/harness doctor

install --local 按项目锁定的版本安装代码（必要时从对应的 v<版本> 标签导出），再写入本机的钩子与插件目录，不改任何入库文件。装好之前，Claude Code 与 Codex 的实时拦截会拒绝一切调用并提示这条命令。

升级

升级需求示例
请从 GitHub 获取 harness 最新版本：https://github.com/windvalley/harness

安装并升级当前项目，保留已有规则和配置，完成迁移检查、验证、评审与交付。需要我操作时，请提供具体步骤。

Agent 应直接从 GitHub 获取最新版本并安装到本机，检查项目当前版本并说明升级影响，准备任务分支及需要的 Worktree，完成验证、评审和必要确认后按交付方式交付，主动报告结果与待处理项。

upgrade 会整份重写 rules/ 与 templates/，项目自己的规范请写在 AGENTS.md 托管块之外；已有配置和黄金任务的迁移由 Agent 核对并说明。

具体命令与其他成员的接续操作见升级参考。

与远程同步

同步需求示例
我想把远程主分支的更新同步到本地。

Agent 应检查差异并说明同步方式和影响，在项目授权范围内处理，最后汇报结果。

远程写入仍须按项目规则单独取得授权，请求本地接入或合并不代表允许推送。下面是同步机制与命令参考。

harness 只管本地主分支。Agent 推送主分支会被拦截，由人推送；Agent 可以推送任务分支，但不能强推。

本地交付下，想让合并后自动推送，在 delivery 里加 "push": true：harness merge 随后把核对过的提交普通推送到远程主分支，不强推、不推标签。它授予推送主分支的权限，所以要人确认，开启的那次合并不推送；主分支受保护、只接受 PR/MR 的仓库请改用远程交付。

接入后优先用 harness sync：它把本地主分支快进到远程主分支，核对远程带来的门禁改动（需要时由人运行 harness confirm --branch origin/main），刷新本机安装并执行 merge.postMergeCommand。本地有远程没有的提交时它拒绝，不改写历史。两种交付方式下都能用，远程交付下它是更新本地主分支的唯一方式，见两种交付方式。

需要人工判断时，也可以用下面两种做法同步远程主分支：

做法一：走一遍本机门禁
git fetch origin
harness verify --branch origin/main
harness review --branch origin/main
harness merge  --branch origin/main
做法二：由人决定信任远程，只能快进
git fetch origin
HARNESS_MAIN_BYPASS=1 git merge --ff-only origin/main

HARNESS_MAIN_BYPASS 是绕过开关，只能由人在自己的终端使用，Agent 设置它会被拦截。

多个会话并行

只要有一个 Agent 在主 Worktree 里切走分支或留下改动，所有任务的合并都会被挡住。并行的项目建议在 policy.json 的 presets 里加上 main-worktree：Agent 不能改主 Worktree 里的文件、不能把它切离主分支，pre-commit 也拒绝主 Worktree 里的提交。
