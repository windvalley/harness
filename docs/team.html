新成员或新机器

入口与客户端配置随仓库分发，门禁代码与 git 钩子留在各自的机器上。工具调用可用时，可以交给 Agent：

说明当前目标
我想在这台新电脑上继续开发这个项目。

Agent 应检查项目锁定的版本，完成本机安装与诊断，并说明需要用户完成的客户端操作。

本机没有安装锁定版本时，已启用的实时拦截可能拒绝所有 Agent 工具调用。此时由人在项目目录的终端先完成安装，再让 Agent 接续诊断：

工具调用被拦截时，由人执行
cd <项目>
node ~/github/harness/bin/harness.mjs install --local
.harness/bin/harness doctor

install --local 按项目锁定的版本安装代码（必要时从对应的 v<版本> 标签导出），再写入本机的钩子与插件目录，不改任何入库文件。装好之前，Claude Code、Codex 与 Antigravity 的实时拦截会拒绝一切调用并提示这条命令。

版本在暂存目录校验完整后才进入正式目录，versions 与 prune 只处理通过校验的正式版本。doctor 分别显示运行中的 CLI、项目 VERSION 与入口锁定版本。清单可确认且内容损坏时，用原版本代码重新安装即可；清单缺失或无效时，先人工检查并移开该目录，工具不会自动覆盖。清理旧版本前先核对其他项目的锁定版本。

init、upgrade、install 和 install --local 都可以加 --dry-run 预检。预览显示实际会改动的项目文件、适用的钩子和客户端配置，以及需要准备的本机共享资源，不写入这些目标。

恢复中断的项目安装

项目写入失败时自动回滚，本机版本、证据密钥和 DeepSeek Harness 插件保持原样。进程被强杀或回滚未完成时，按 doctor 提示在原 Worktree、原分支和原提交运行 harness install --recover。

项目入口不可用时，从新版源码恢复
node ~/github/harness/bin/harness.mjs install --recover

恢复不覆盖中断后的人工改动。发生冲突时保留这些改动和私有备份，核对提示后再重试。

跨会话交接

需要换会话、换执行者或把任务上下文贴到 PR/MR 时，从现有状态生成 Markdown 交接视图：

只读生成交接
harness status --handoff --branch feature/login

视图汇总分支与主分支完整提交、方案文件、有效实施授权、验收清单、Worktree 未提交改动、验证与评审证据、阻塞、相关上报、下一步命令和恢复入口。缺省分支是当前分支，退出语义与普通 status 相同。

它不运行验证或评审，不写交接文件、账本或新的状态真源。外部副作用与恢复点没有结构化记录时会明确提示，接手者仍须核对实际环境。动态正文会遮盖常见凭据，但粘贴到外部系统前仍须人工检查。

升级

升级需求示例
请从 GitHub 获取 harness 最新版本：https://github.com/windvalley/harness

安装并升级当前项目，保留已有规则和配置，完成迁移检查、验证、评审与交付。需要我操作时，请提供具体步骤。

Agent 应直接从 GitHub 获取最新版本并安装到本机，检查项目当前版本并说明升级影响，准备任务分支及需要的 Worktree，完成验证、评审和必要确认后按交付方式交付，主动报告结果与待处理项。

upgrade 按 managed-files.json 的哈希更新 rules/ 与 templates/。本地修改、非普通文件或符号链接会在预览和正式升级时形成冲突；先迁移项目自己的说明，确需覆盖时由人明确运行 upgrade --force。已有配置和黄金任务的迁移由 Agent 核对并说明。upgrade --force 的人工执行要求目前只有流程规范约束，没有专门的 Agent 拦截规则，见授权与执行矩阵。

具体命令与其他成员的接续操作见升级参考。

与远程同步

同步需求示例
我想把远程主分支的更新同步到本地。

Agent 应检查差异并说明同步方式和影响，在项目授权范围内处理，最后汇报结果。

远程写入仍须按项目规则单独取得授权，请求本地接入或合并不代表允许推送。下面是同步机制与命令参考。

harness 只管本地主分支。Agent 推送主分支会被拦截，由人推送；Agent 可以推送任务分支，但不能强推。

本地交付下，想让合并后自动推送，在 delivery 里加 "push": true：harness merge 随后把核对过的提交普通推送到远程主分支，不强推、不推标签。它授予推送主分支的权限，所以要人确认，开启的那次合并不推送；主分支受保护、只接受 PR/MR 的仓库请改用远程交付。

接入后优先用 harness sync：它把本地主分支快进到远程主分支，核对远程带来的门禁改动（需要时 Agent 先运行 harness confirm --branch origin/main 展示摘要，再由人运行 .harness/bin/harness confirm --branch origin/main --yes），刷新本机安装并执行 merge.postMergeCommand。本地有远程没有的提交时它拒绝，不改写历史。两种交付方式下都能用，远程交付下它是更新本地主分支的唯一方式，见两种交付方式。

需要人工判断时，也可以用下面两种做法同步远程主分支：

做法一：走一遍本机门禁
git fetch origin
harness verify --branch origin/main
harness review --branch origin/main
harness merge  --branch origin/main
做法二：由人决定信任远程，只能快进
git fetch origin
HARNESS_MAIN_BYPASS=1 git merge --ff-only origin/main

HARNESS_MAIN_BYPASS 是绕过开关，只能由人在自己的终端使用，Agent 设置它会被拦截。

多个会话并行

主 Worktree 切离主分支、存在已跟踪文件的未提交改动或有 Git 操作进行中时，合并和同步都会阻塞。未跟踪或忽略的文件只在与本次目标检出冲突时阻塞，其余原样保留。

新项目的 init 默认启用 main-worktree：Agent 不能改主 Worktree 里未被忽略的文件、不能把它切离主分支，pre-commit 也拒绝主 Worktree 里的提交。已有项目升级时不自动开启；可从 presets 删除它来关闭，只需人工在主 Worktree 提交时也可只关闭 main-worktree-commit。
