harness 使用教程

跑在本机的 AI-Native 研发流程，让 Agent 在 git 项目里高质量地完成从需求到合并的全过程。你和 Agent 聊清需求、同意实施后，Agent 连续完成实现、测试、验证和独立评审，直到合入主分支；能否合入由门禁机械判定，你只需在交付时验收结果。

  • 本机运行，不依赖云端 CI
  • 没有 npm 依赖
  • Node.js 20+
  • git 2.38+
  • macOS / Linux
  • MIT 许可
快速开始 看架构图 参考手册

它解决什么问题

Agent 已经能写代码、写测试、跑检查，但要放心让它从需求一路做到合并，还要防住它常犯又不自知的错：

  • 读到 .env、私钥，或者把它们写进命令外发；
  • 用 git reset --hard、git stash、rm -rf、强推，丢掉自己或别人的改动；
  • 测试没跑或没跑全，就宣布“完成”；
  • 直接在主分支上提交，或者为了让检查通过，顺手把检查规则改松；
  • 大需求不先对齐方案就动手，改完才发现方向不对。

写进提示词或规范里的要求，Agent 未必每次都遵守。harness 把研发流程写成项目规范，并把其中能机械判定的要求变成门禁：由程序在本机判定、拦截并记录，Agent 照着拦截信息改道继续。你只需聊清需求、同意实施，再在交付时验收；中间的实现、测试、验证、评审与合并由 Agent 连续完成。

当场纠正

危险的工具调用在执行之前被拦下，拦截信息带着原因和正确做法。

结果把关

没有签名的验证证据和独立评审，改动进不了主分支，对所有客户端和人都一样。

放宽不了自己

任务分支改了规则也不影响它自己的判定，门禁改动合并前必须由人确认。

本机、可审计

判定都在本机完成，记录签名后存进仓库自己的 git 目录，随时可以核对。

架构总览

三层防线

一次改动从 Agent 调用工具开始，到写进主分支为止，要依次经过三层检查。前两层在过程中纠正，第三层在结果上把关。

层何时生效管什么覆盖谁
① 实时拦截Agent 每次调用工具之前读取密钥、改写门禁入口、不可逆的 git 操作、绕过开关Claude Code、Codex、DeepSeek Harness
② git 钩子每次提交与引用更新提交信息、暂存的密钥文件、主分支的写入所有客户端和人
③ 受控合并合并到主分支时验证证据、独立评审、门禁改动的人工确认所有客户端和人

即使某个客户端没有接上实时拦截（例如 Codex 还没信任钩子），git 层的提交检查和主分支保护照样有效，没有证据和评审的改动依然进不了主分支。

组件与数据放在哪

项目里只入库配置和一个很小的入口脚本，门禁代码、密钥和运行记录都留在本机。

位置内容入库
.harness/config.json、policy.json、verify.json项目参数、拦截规则、检查映射是
.harness/golden/tasks.json对规则本身的回归用例（黄金任务）是
.harness/rules/、.harness/templates/给 Agent 读的研发规范与模板，升级时整份重写是
.harness/bin/harness、.harness/VERSION入口与锁定的版本号是
.claude/settings.json、.codex/hooks.json客户端的实时拦截配置是
AGENTS.md 托管块Agent 每次都会加载的硬性要求是
.git/hooks/pre-commit、commit-msg、reference-transaction默认否
.git/harness/证据、评审、确认、授权记录与账本，所有 Worktree 共用否
~/.local/share/harness/按版本安装的门禁代码与签名密钥否
~/.cache/harness/checkouts/verify 的固定检出否

核心原理

一次任务的生命周期

每一步都会留下一条签名记录，并且绑定到具体的内容上。内容一变，对应的记录就作废，需要重跑那一步。这样合并时核对的永远是“这一份代码”的证据，而不是“某个时候跑过一次”。

  • verify 在固定检出里检出分支提交，只验证已提交的内容；工作区里没提交的改动不算。
  • review 要求先有通过的验证证据，评审结论同样绑定分支提交。
  • confirm 只在改动涉及门禁本身（配置、规则、入口、钩子）时需要，绑定的是合并结果的 tree。
  • merge 发现没有证据，或主分支的新改动波及某些检查时，会自己重跑这些检查；评审不会自动重做。

签名记录

证据、评审、确认与实施授权都是 JSON 记录，用本机密钥 ~/.local/share/harness/evidence.key（权限 600）做 HMAC-SHA256 签名，存在仓库的 .git/harness/ 下，所有 Worktree 共用，另有一份追加式账本 ledger.jsonl。

记录被改动、密钥轮换或丢失时，签名校验失败，harness 会指出该重跑哪一步（例如 harness verify --branch <分支>），而不只是报“签名不匹配”。

主分支只认合并令牌

主分支的保护不靠“约定不要直接提交”，而是由 git 自己的 reference-transaction 钩子执行：每次更新 refs/heads/main 时，钩子都要求环境里带着合并令牌。

所以在主分支上 git commit 或 git pull 被拒绝是预期行为。同步远端主分支的做法见 团队与多机。

配置只从主分支读取

如果任务分支能改规则并立即生效，Agent 就可以“先关掉检查再提交”。harness 的所有判定（实时拦截、git 钩子、verify 选检查、merge 的合并条件）都从主分支的 git 对象读取配置，不读工作区，也不读任务分支。

  • 门禁文件包括 .harness/ 下的配置、规则、用例与入口，客户端配置和钩子目录，以及 governance.gatePaths 追加的路径。
  • Agent 执行带 --yes 的确认会被拦截，确认必须由人执行；确认后如果分支再提交或主分支前进导致合并结果变化，要重新确认。
  • 首次接入时主分支上还没有配置，这时按接入分支提议的配置执行，并且无论改了什么都要人确认；确认后以快进方式合入，这份配置从此成为信任根。
  • 改规则之前可以用 harness golden --worktree 按工作区的配置重放黄金任务，确认新规则的判定符合预期。

按改动选检查

verify 不是每次全量跑测试，而是按 .harness/verify.json 的映射，用“分支相对合并基线改了哪些路径”选出要跑的检查：

verify.json 片段
{ "id": "web-typecheck", "tier": "gate",
  "when": ["web/src/**", "web/package.json"],
  "cwd": "web", "cmd": ["pnpm", "typecheck"],
  "requires": ["web/node_modules"] }
tier含义
gate必过，失败就不能合并
extended不自动执行，记入证据的“未执行”清单，并附补验方式
advisory只提示，不计入未执行
  • 检查在固定检出 ~/.cache/harness/checkouts/<哈希>/work 里执行，它是一个分离头指针的 Linked Worktree，不受你工作区状态影响，增量缓存可以复用。
  • requires 里的依赖目录（如 node_modules）从主 Worktree 软链接进检出；缺失时证据记为 incomplete，不能评审与合并。
  • 命令不存在时证据里单独标出“未找到命令”，说明是缺工具，不是代码有问题。
  • harness verify --plan --branch <分支> 只列出会执行的检查，不执行。

独立评审

写代码的 Agent 很难客观评价自己的改动。review 启动一个不了解实现过程的评审进程，只给它评审材料：验收清单、验证证据摘要、提交说明、改动文件统计和 diff，从“需求符合度”和“工程质量”两个维度给出结论。

  • 后端默认 auto：本机有 claude 就用它，否则用 codex；都没有时可以接入任意命令（command 后端）。
  • claude 后端不开放任何工具、不加载项目设置；codex 与 command 后端在空的临时目录里运行，读不到项目文件。
  • 有 high 或 critical 级别的发现时拒绝合并，级别可以用 review.blockSeverities 调整。
  • 提交说明标明是实现方自述，只用来理解意图；说法与 diff 不符时，评审会作为发现报出来。
  • diff 超过 review.maxDiffChars（默认 300000 字符）时拒绝评审，并按目录给出拆分建议。
  • 有验收清单 .harness/acceptance/<分支名>.md 时评审逐条核对，需求符合度为 unknown 或 unmet 都会被拒绝。

任务分级与实施授权

规则写在 .harness/rules/core.md，要点同时写进 AGENTS.md 的托管块，Agent 开始任务前先判断分级：

直接实施

小优化、小迭代或缺陷修复：不改库表与迁移，不改接口契约、权限与数据兼容性，代码改动少于 500 行（测试、文档、锁文件不计）。

先方案后实施

其余任务和拿不准的任务：先探索仓库，一次问一个问题，写出验收清单、spec 与 plan，提交后停下等你授权。

默认启用的 plan-first 预设把“停下等授权”变成门禁：

  • 任务分支写了实施方案（默认 docs/changes/*/plan.md）、还没有授权记录时，Agent 只能写方案与验收清单，写测试和代码会被拦截。
  • 你在对话里说“开始实施”之类的话就是授权，不需要执行命令。Agent 会运行 harness approve --branch <分支> --yes --note "<你的原话>" 照录原话。
  • 写了方案、改了库表相关文件或代码改动超过阈值的分支，没有授权记录不能合并（plan_unapproved）。
  • 合并输出与 harness status 会显示记录下来的原话，你可以随时核对。

实施默认先红后绿：先把每条验收写成测试并确认失败，再实现到全部通过。

版本锁定的入口

门禁代码如果放在项目里，Agent 就可以改它。所以项目只入库一个入口 .harness/bin/harness，它按 .harness/VERSION 锁定的版本，转发到本机的 ~/.local/share/harness/versions/<版本>/。

  • 版本目录带内容哈希清单，harness doctor 会校验它没有被就地改写。
  • 入口与钩子 Agent 不能手改，只能在任务分支运行 harness install、init 或 upgrade 重新生成，合并前同样要人确认。
  • 入口随仓库分发，每个 Linked Worktree 检出即可用；同一台机器上的多个项目可以锁定不同版本。

快速开始

需要：macOS 或 Linux，Node.js 20 及以上，git 2.38 及以上（合并用到 git merge-tree --write-tree），以及本机已登录的 claude（Claude Code CLI）或 codex，用来做独立评审。

  1. 在项目里向 Agent 提出接入请求

    在 AI 编程客户端中打开待接入项目，说出接入目标并提供仓库地址即可。Agent 应先阅读来源仓库的 README 和接入说明，检查环境、查找本机已有的 harness，没有时从官方仓库获取；没有 npm 依赖，也不需要全局安装。

    接入需求示例
    我想给当前项目接入 harness：https://github.com/windvalley/harness

  2. 查看接入方案与检查配置

    Agent 调查并预览接入改动，按项目规则准备任务分支和工作环境，再写入配置、提交、验证与独立评审。用户不需要先创建 Worktree，也不一律需要新建一个；同目录任务分支、已有隔离工作区或新建 Linked Worktree 都按实际约束选择。

    init 会写入配置、规则、入口、git 钩子、客户端配置和 AGENTS.md 托管块。起始检查需要对照项目真实命令核实，占位与未执行项应明确列出。

    已有 husky、自定义钩子等其他门禁时，Agent 应说明保留或迁移方式，需要舍弃现有规则时先由你决定。详细命令见参考手册。

  3. 亲自确认门禁改动，再让 Agent 继续

    首次接入走受控合并时，Agent 展示涉及的门禁文件、将生效的规则与检查项，并给出包含实际路径和分支的确认命令。看过摘要后，由你在自己的终端执行带 --yes 的确认；在 Claude Code 中也可以用 ! 前缀亲自执行。

    对话里的同意不能代替这条人工确认。执行后告诉 Agent“已确认，请继续”，由它完成已获授权的本地合并并汇报结果。

  4. 让客户端用上实时拦截

    • Claude Code：重启正在运行的会话，钩子在会话启动时读入。
    • Codex：运行 /hooks，进入 Review hooks 后按 t 信任；每个 Worktree 首次使用时各信任一次。
    • DeepSeek Harness：每台机器为用到的 profile 注册一次本机插件，所有项目共用，注册后重启。桌面版要用 App 自带的命令行，先打开一次桌面版再完全退出后运行；浏览器版用 dsh：
    # 桌面版
"/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh" plugin --profile desktop add ~/.local/share/harness/dsh-plugin
# 浏览器版
dsh plugin --profile web add ~/.local/share/harness/dsh-plugin

    完成当前客户端的操作后，告知 Agent 已完成即可，由它接续诊断并解释已验证与仍待验证的部分，下面是输出示意：

    输出节选
      [ok] git:reference-transaction: <项目>/.git/hooks/reference-transaction
  [ok] client:claude: PreToolUse 已接入（CLI 已验证；桌面版仅静态确认，未端到端实测）
  [!!] client:codex: 钩子已接入但尚未信任：在 Codex 里运行 /hooks 批准一次，否则命令不会经过门禁
  [ok] project:main: 配置取自主分支 main
  [ok] main-worktree: <项目> 停在 main 且洁净，可以接收合并

    [!!] 表示需要处理，[?] 表示仍待验证。配置就位、产品曾经实测与当前客户端实际调用已验证分别说明，不能只凭初始化成功宣布全部接入完成。

  5. 检查结果，保留任务工作区

    确认接入已按约定合入，真实检查与验证、评审证据齐全，诊断中的待处理项有明确解释。接入分支和任务 Worktree 保留，需要清理时再按清理流程发起请求。

项目规则允许、没有其他门禁且你明确选择不走受控评审的小项目，可采用主分支直接接入的简化方式。由 Agent 先说明区别，再由你决定，见参考手册。

日常工作流

规则已经写进项目（AGENTS.md 托管块与 .harness/rules/），用平常的话描述想法、问题或希望的变化即可。理解需求、澄清关键问题、整理验收标准和交付结果由 Agent 主动负责。下文的 harness 都指项目里的入口 .harness/bin/harness。

如何表达需求与后续协作

下面是两个普通需求示例，不是必须照抄的提示词模板。用户不需要预先填齐验收标准、安排工作流程或重复交付要求，实际分级由 Agent 核对仓库后判断。

大需求：先讨论，再授权实施

描述想法即可
我想让系统支持多个企业使用，企业之间看不到彼此的数据，每个企业还能管理自己的成员和权限。

这类需求涉及数据隔离与权限。Agent 应先了解现状，再与你讨论企业边界、角色权限和已有数据兼容等关键问题，主动整理验收清单、行为说明与实施方案。

关键问题已明确或由你标为待定后，Agent 应保留未决问题并说明影响，主动进入方案，不需要你宣布问题问完或指挥写文档。方案交付后它应停下，等待你明确同意实施该方案。

最初表达需求不替代方案交付后的实施授权，对某个澄清答案或方案细节的认可也不等于同意实施。授权不要求固定措辞。

小需求：核实范围后可以直接实施

描述希望的变化即可
列表没有数据时，我希望显示“暂无数据”。

Agent 核实这只是已有列表页的局部调整，不改接口、数据或权限且满足小任务条件后，可以直接实施，并验证空列表和正常列表的表现。发现影响超出小任务范围时，应转入讨论、方案和授权流程。

用户当前只要求分析、评估或讨论时仍保持只读，不能因为需求看起来小就动手。用户也可以补充约束或调整节奏。

一次任务

两类任务都由 Agent 整理验收标准，关键业务含义有歧义时再与你确认，按相应流程准备任务分支及需要的 Worktree，执行验证和独立评审，再按项目授权处理本地合并。用户不需要额外提醒它汇报效果入口、验收结果和最终合并状态。

  • 看阶段：大需求先讨论并交付方案，明确授权后才实施；小需求核实范围后可以直接实施。
  • 看效果：从约定入口查看已经实施的结果；例如小需求中空列表显示“暂无数据”，有数据时列表正常。
  • 看证据：验收逐条对应需求，验证与独立评审有结果，未执行项与阻塞明确列出。
  • 看状态：说明已合并、待授权合并还是被阻塞，并给出分支、提交与工作区位置。

Agent 可以通过 status 汇总还差什么。下面示例表示门禁条件已满足，但没有验收清单，需求符合度仍是 unknown，不能据此宣布用户需求已经验收通过：

分支 feat/login -> main

  [ok] branch: 待合入 5685e8a474 -> main
  [ok] main-worktree: 主 Worktree 停在 main 且洁净
  [ok] evidence: 验证通过，主分支自验证以来新增 0 个文件，未波及已执行的检查，可直接复用
  [ok] review: 评审通过（需求符合度 unknown，工程质量 good，清单来源 无）
  [ok] plan: 属于直接实施的范围（代码改动 1 行），不需要实施授权
  [ok] gate: 本次没有改动门禁配置与规则
  [-] acceptance: 验收清单约定位置：acceptance/feat-login.md（存在时评审会核对需求符合度）

可以合并：harness merge --branch feat/login
  • 合并前的工作区检查、常规冲突处理和重新验证由 Agent 按项目规则执行。
  • 涉及用户已有改动或业务意图无法判断时，Agent 说明具体分歧，交由你决定。

执行命令与合并条件见一次任务参考。

验收清单

清单放在 .harness/acceptance/<分支名>.md，分支名里的 / 等字符换成 -，例如 feat/login 对应 feat-login.md。每条写成能用测试或命令验证的结果。没有清单时评审只评工程质量；intent.mode 设为 required 时没有清单不能合并。

提交信息

默认规范分两处检查：commit-msg 钩子要求标题是 类型: 说明 或 类型(范围): 说明；merge 进一步要求标题之后空一行，其余每行都是 - 开头的要点。

git commit -m "feat(login): 支持短信验证码登录" -m "- 新增验证码发送与校验接口
- 登录页增加验证码输入"

每个 -m 是一段，多条要点要写在同一个 -m 里换行。只有标题的提交能通过钩子，但合并时会报 bad_commit_message。

清理任务 Worktree

合并后保留任务 Worktree 和分支，因为会话可能还停在里面。需要清理时向 Agent 发起请求：

清理需求示例
我想清理已经完成的任务工作区。

Agent 应先给出预览，列出具体目录、分支、会连带删除的本机文件和跳过原因，不立即删除。看过预览并明确确认具体对象后再清理；含本机文件的目录需要单独明确同意，主 Worktree、命令所在 Worktree 和验证检出会保留。

预览还会检查提交是否已合并、新任务保护、未提交文件、进程和锁定情况。详细条件和命令见清理参考。

被拦截时怎么办

在已授权的任务中，Agent 应主动解释拦截原因并按规则处理常规改道和重跑，不需要用户另发调度指令。需要业务判断、授权或亲自执行时，由它说明具体事项；如果想了解原因，直接问“刚才为什么被拦住了？”即可。

拦截信息包含原因、对象、正确做法和规则 id，Agent 照着“正确做法”改道即可：

[harness] 已拦截: 强制推送会覆盖远端历史
对象: git push --force origin main
正确做法: 普通推送到任务分支；确需强推请用户明确授权具体分支
规则: git-force-push
拒绝直接更新 refs/heads/main(5685e8a474 -> 5d3ce6d65d)
本地主分支只允许由 harness merge 更新，它会先核对证据与评审。
正确做法: 在任务分支提交后运行 harness merge --branch <任务分支>。

常见的合并拒绝原因：

提示处理
bad_commit_message分支上有提交不符合合并时的格式；在任务分支改写提交信息，再重新 verify、review
review_missing / review_blocked运行 harness review；被拒时按发现修复，提交后重新 verify、review
gate_change_unconfirmedAgent 展示确认摘要；由人在自己的终端执行它给出的带 --yes 的确认命令，再告诉 Agent 继续
plan_unapproved大改动没有实施授权记录；补齐方案，你同意后由 Agent 照录原话运行 harness approve
conflict在任务分支上 git merge main 解决冲突，再重新验证与评审
main_moved合并过程中主分支前进了，重新运行 harness merge，已有证据会复用
验证结果 incompleterequires 里的依赖目录在主 Worktree 不存在，装好依赖后重跑
主 Worktree 不在 main 或不洁净Agent 先核对状态并保留已有改动，按项目规则准备主 Worktree；需要处置用户改动时先说明具体对象并取得授权

更多见参考手册的常见问题。手工判定一条命令会不会被拦：harness check --kind shell --command "<命令>"；列出所有生效规则：harness rules。

按项目定制

可以直接对 Agent 说“请检查当前规则和检查配置，按项目实际情况提出调整方案，说明影响并按授权实施”。配置改动仍按门禁流程验证、评审和人工确认。

四个文件决定门禁的行为，Agent 可以直接改，但它们都属于门禁改动，合并前要人确认，合入后才生效。

config.json

主分支名、合并要求、提交格式、评审后端、验收清单模式、任务分级阈值、Worktree 清理命令。

verify.json

改了哪些路径跑哪些检查、检查的级别、执行目录与依赖。

policy.json

启用哪些预设、关掉哪些规则、项目自己的拦截规则。

golden/tasks.json

对规则本身的回归用例，改坏规则的分支在 verify 阶段就被拦下。

加一条项目规则，例如禁止改已上线的迁移基线：

policy.json 片段
{
  "id": "migration-baseline",
  "kind": "write-protect",
  "paths": ["db/migrations/0001_*.sql"],
  "reason": "迁移基线已经上线，改它会让已部署的库与代码不一致",
  "fix": "新增一个迁移文件，不要改已有的基线"
}

每条规则都要写 reason 和 fix，拦截时原样展示给 Agent。默认启用的预设：

预设内容
secrets禁止读取、写入或用命令外发 .env、私钥、凭据与证据密钥
git-safety拦截递归删除、丢弃改动、强删 Worktree、删分支、强推、stash、--no-verify，以及在主分支上合并、变基、重置
gate-self保护执行器入口与绕过开关；轮换密钥与人工确认只能由人执行
plan-first没有实施授权时只能写方案文件，大改动合并前必须有授权记录
main-worktree（可选）主 Worktree 只用来合并，多个会话并行时推荐启用

字段的完整说明见参考手册的配置一节。

团队与多机

新成员或新机器

入口与客户端配置随仓库分发，门禁代码与 git 钩子留在各自的机器上。工具调用可用时，可以交给 Agent：

说明当前目标
我想在这台新电脑上继续开发这个项目。

Agent 应检查项目锁定的版本，完成本机安装与诊断，并说明需要用户完成的客户端操作。

本机没有安装锁定版本时，已启用的实时拦截可能拒绝所有 Agent 工具调用。此时由人在项目目录的终端先完成安装，再让 Agent 接续诊断：

工具调用被拦截时，由人执行
cd <项目>
node ~/github/harness/bin/harness.mjs install --local
.harness/bin/harness doctor

install --local 按项目锁定的版本安装代码（必要时从对应的 v<版本> 标签导出），再写入本机的钩子与插件目录，不改任何入库文件。装好之前，Claude Code 与 Codex 的实时拦截会拒绝一切调用并提示这条命令。

升级

升级需求示例
我想升级当前项目使用的 harness。

Agent 应检查当前版本，与你明确目标版本并说明升级影响，准备任务分支及需要的 Worktree，完成验证、评审和必要确认后的已授权本地合并，主动报告结果与待处理项。

upgrade 会整份重写 rules/ 与 templates/，项目自己的规范请写在 AGENTS.md 托管块之外；已有配置和黄金任务的迁移由 Agent 核对并说明。

具体命令与其他成员的接续操作见升级参考。

与远端同步

同步需求示例
我想把远端主分支的更新同步到本地。

Agent 应检查差异并说明同步方式和影响，在项目授权范围内处理，最后汇报结果。

远程写入仍须按项目规则单独取得授权，请求本地接入或合并不代表允许推送。下面是同步机制与命令参考。

harness 只管本地主分支。Agent 推送主分支会被拦截，由人推送；Agent 可以推送任务分支，但不能强推。同步远端主分支有两种做法：

做法一：走一遍本机门禁
git fetch origin
harness verify --branch origin/main
harness review --branch origin/main
harness merge  --branch origin/main
做法二：由人决定信任远端，只能快进
git fetch origin
HARNESS_MAIN_BYPASS=1 git merge --ff-only origin/main

HARNESS_MAIN_BYPASS 是绕过开关，只能由人在自己的终端使用，Agent 设置它会被拦截。

多个会话并行

只要有一个 Agent 在主 Worktree 里切走分支或留下改动，所有任务的合并都会被挡住。并行的项目建议在 policy.json 的 presets 里加上 main-worktree：Agent 不能改主 Worktree 里的文件、不能把它切离主分支，pre-commit 也拒绝主 Worktree 里的提交。

信任模型与限制

harness 防的是 Agent 的误操作，以及被提示注入后常见的绕过写法；不防拥有本机权限、有意破坏的人或进程。

  • 签名密钥在你的用户目录里，能读到它的进程就能伪造记录。密钥损坏或怀疑泄露时，由人运行 harness key rotate --yes，已有记录全部作废。
  • HARNESS_MAIN_BYPASS 等环境变量与 core.hooksPath 能让门禁失效，只能由人使用，Agent 设置或读取会被拦截。
  • 路径规则只约束写文件、读文件类的工具调用；用 shell 命令读写同一个文件，要靠命令规则覆盖。
  • Codex 没有信任钩子时没有实时拦截；DeepSeek Harness 的本机插件尚未在运行中的客户端里端到端实测；Claude 桌面版只做了静态确认。git 层对它们都生效。
  • 任务分级与先红后绿仍由 Agent 判断，门禁只兜底能机械判定的部分；授权记录里的原话要靠你在合并输出或 harness status 里核对。
