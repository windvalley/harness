harness 使用教程

harness 是一套面向 AI 编程 Agent 的 AI-Native 研发流程与交付门禁。Agent 主导从需求到交付的完整研发过程，通过自动化验证、独立评审和门禁把关质量，你只需参与关键决策和最终验收。

  • 门禁不依赖云端 CI
  • Node.js 20+
  • git 2.38+
  • macOS / Linux
  • MIT 许可

它解决什么问题

Agent 已经能写代码、写测试、跑检查，但要放心让它从需求一路做到交付，还要防住它常犯又不自知的错：

  • 读到私钥、凭据，或者把它们写进命令外发；
  • 用 git reset --hard、git stash、rm -rf、强推，丢掉自己或别人的改动；
  • 测试没跑或没跑全，就宣布“完成”；
  • 直接在主分支上提交，或者为了让检查通过，顺手把检查规则改松；
  • 大需求不先对齐方案就动手，改完才发现方向不对。

写进提示词或规范里的要求，Agent 未必每次都遵守。harness 把研发流程写成项目规范，并把其中能机械判定的要求变成门禁：在本机判定、拦截并记录。小任务核实范围后可直接实施，大需求要先完成方案并获得实施授权。检查或评审不通过时，Agent 按原因修复并重新验证；遇到门禁变更、权限不足、业务决策或无法自行解决的问题时再请你介入。门禁只检查已配置并实际生效的条件，具体边界见信任模型与限制。

当场纠正

危险的工具调用在执行之前被拦下，拦截信息带着原因和正确做法。

结果把关

通过 harness merge 或 harness submit 交付时，缺少必需的验证证据、独立评审或授权确认就会被拒绝；平台合并仍由平台保护规则把关。

放宽不了自己

任务分支改了规则也不影响它自己的判定，门禁改动交付前必须由人确认。

本机、可审计

判定都在本机完成，记录签名后存进仓库自己的 git 目录，随时可以核对。

一个需求怎么交付

阶段Agent 做什么由什么保证
理解与澄清读仓库、判断任务分级；大需求逐个澄清关键问题，写出验收清单、行为说明与实施方案，配置了评审者时先让另一个模型审一轮方案（只给建议，不是门禁），然后停下，等你同意实施启用方案优先钩子时，未授权方案任务不能提前写代码；交付时还会核对必要的实施授权记录
实施先把每条验收标准写成单元、集成或 E2E 测试并确认失败，再实现到全部通过；只在缺权限、需要业务拍板等情况下停下读取密钥、不可逆的 git 操作等危险调用当场被拦下，Agent 按提示改道继续
验证在固定检出里按改动路径执行自动检查；需要真实浏览器或登录态的检查在外部运行后，用 attest 登记结果自动证据绑定提交；外部证据绑定检查定义和它覆盖的文件，改到相关内容才需要重验
独立评审由不了解实现过程的评审进程按合并前验收清单核对需求符合度，并评工程质量；被拒时按发现修改后重新验证、评审合并前需求未满足或有高危发现即拒绝；合并后验收单独跟踪
交付到主分支本地交付运行 harness merge 合入主分支；远程交付运行 harness submit 推送核对过的提交并创建或更新 PR/MR，由你或团队在平台上合并两条路都先核对证据与评审对最新提交仍然有效；本地主分支只接受 harness merge 与 harness sync 写入
交付逐条给出验收证据、交付状态与待处理项；有合并后检查时，在实际合入后继续完成并登记由你最终验收；status 会分清“已合入”和“合并后验收完成”

小需求核实范围后跳过方案，直接从实施开始。任务分级和先红后绿由 Agent 按项目规范执行，门禁兜底其中能机械判定的部分：配置了 testFirst 与 coverage 的项目，验证会复算“还原实现后新增的测试必须失败”和“改动行必须被测试执行到”，见信任模型与限制。

两种交付方式

本地交付（默认）远程交付（PR/MR）
适合由 Agent 本地合并的项目，也可以有远程仓库要求在 GitHub 或 GitLab 上审核并合并 PR/MR 的项目
门禁通过后harness merge 合入本地主分支harness submit 推送任务分支，创建或更新 PR/MR
谁来合并Agent，在项目授权范围内你或团队在平台上合并，harness 不代为合并
推送主分支默认由你推送；配置 "push": true 后由 harness merge 合入后推送不适用，推送与合并走 submit、sync 和平台
本地主分支怎么更新harness merge平台合入后用 harness sync 快进
需要准备无本机安装并登录 gh（GitHub）或 glab（GitLab）

两种方式只能选一种，由主分支上 .harness/config.json 的 delivery 决定：本地交付下 submit 会被拒绝，远程交付下 merge 会被拒绝；sync 只同步远程主分支，两种方式下都能用。默认是本地交付，init 写入 "delivery": { "mode": "local" }，没有这一段的项目也按本地交付处理。

远程交付下，harness 保证它提交的 PR/MR 通过了本机门禁；平台上最终合入什么，由团队在平台上配置的保护规则把关。

接入时就想用 PR/MR，告诉 Agent 平台是哪个，接入分支本身就以 PR/MR 提交。已经接入的项目改用 PR/MR，对 Agent 说明即可：

切换需求示例
这个项目改用 PR/MR 交付，平台是 GitHub。

  1. 你准备平台命令

    在本机安装并登录 gh 或 glab；本地主分支有没推送的提交时先推送，让本地与远程主分支一致。

  2. Agent 在任务分支改交付设置

    把 delivery 改为 { "mode": "remote", "provider": "github" }，验证、评审后给你看确认摘要，摘要里写明它由此获得的推送任务分支和创建 PR/MR 的权限。

  3. 你确认，Agent 提交 PR/MR

    你执行确认命令后，Agent 运行 harness submit，把这个改动本身作为 PR/MR 提交。

  4. 平台合并后同步

    你在平台上合并后，Agent 运行 harness sync，此后就改走 PR/MR。

改回本地交付按同样的步骤把 mode 改回 local。交付方式的任何变化都要你确认，不受其他开关影响，详见参考手册。
