被拦截时怎么办

理解常见拦截与拒绝原因，按提示恢复任务。

在已授权的任务中，Agent 应主动解释拦截原因并按规则处理常规改道和重跑，不需要用户另发调度指令。需要业务判断、授权或亲自执行时，由它说明具体事项；如果想了解原因，直接问“刚才为什么被拦住了？”即可。

拦截信息包含原因、对象、正确做法和规则 id，Agent 照着“正确做法”改道即可：

[harness] 已拦截: 强制推送会覆盖远端历史
对象: git push --force origin main
正确做法: 普通推送到任务分支；确需强推请用户明确授权具体分支
规则: git-force-push
拒绝直接更新 refs/heads/main(5685e8a474 -> 5d3ce6d65d)
本地主分支只允许由 harness merge 更新，它会先核对证据与评审；从远程主分支快进用 harness sync。
正确做法: 在任务分支提交后运行 harness merge --branch <任务分支>。

远程交付的项目，提示改为运行 harness submit --branch <任务分支> 创建或更新 PR/MR，平台合入后运行 harness sync。

验证入口失败后先判断什么

验证入口失败不等于验收失败。 Agent 应先确认哪条必要验收仍缺证据、命令是否已经进入目标行为，以及项目是否允许覆盖同一行为的定向验证入口。 例如全局 UI 台账在浏览器启动前失败时，可以按项目规则用真实页面的定向浏览器测试验证受影响交互；只加载页面或只跑静态检查不能代替交互验收。

声称“既有问题”需要已有报告、同条件定向基线复现或可比日志，不能只凭文件未修改或非零退出码判断。 最小诊断有合法恢复路径时继续执行，不默认全量基线排查、不扩修无关问题；必要验收仍不可行且需要权限、业务判断或超出授权的修改时，才上报交给人决定。

每项验证结果提供 outcome 与 reasonCode，最终执行计划保留检查 ID、命令和目录。 普通非零只记为 command_failed，必须结合日志归因，不能猜是断言失败或环境故障。

结果原因下一步
missing_command、spawn_error命令未找到或进程未启动，核对工具安装、PATH、执行目录和权限
timeout、signal命令超时或被信号结束，核对日志与运行条件
missing_dependency、invalid_config、required_uncovered补齐依赖、修正配置或必验路径映射；门禁配置改动仍须人工确认
command_failed命令已启动但非零退出，读取具体失败报告后确定修复方向
check_failedHarness 内建 TDD 或覆盖率条件未满足，例如没有新测试、低于阈值或没有生成报告
fail_fast、prerequisite_failed该项尚未运行，查看 blockedBy 中的上游检查 ID，先处理前置问题

已知阻塞标为 blocked，连带未执行标为 not_run，都不会被当成通过。 必需 gate 仍须通过，合法的定向外部证据不能让失败的 gate 自动通过；合并前 extended 仍是可选检查，未登记时如实披露，不自动升级为硬门禁。

技术阻塞消除后

技术修复或等价验收证据已经消除原阻塞时，Agent 可用 escalate resolve 记录解除原因与证据引用，继续完成验证和交付。

harness escalate resolve --id esc-1a2b3c4d --reason "定向浏览器验收已通过" --evidence "output/ui/report.md"

resolve 只接受 open 状态的上报，保留原始上报，不生成答复。 它不是人工 answer，不替用户选择方案，也不改变门禁、授权或人工确认要求。 命令只保存非空证据引用，不解析引用或证明验收通过，外部检查仍用 attest 登记。

open 使用可信的本地提交 SHA 和成功读取的待验收义务 key 快照绑定上报，未填写分支时使用当前分支。 收尾检查只接受分支、提交和义务快照一致、未解除的上报；新提交、义务集合变化或技术解除后，继续核对剩余交付义务。 输入的 head、obligations、bindingStatus 和 bindingProblem 不能替代命令读取的结果。

合法的计划中、仅有远端引用或已删除分支无法取得可信绑定时，仍可保存通用上报。 义务读取失败也可留档，但记录标为 context.bindingStatus=unbound，并在 bindingProblem 保留脱敏诊断，不填可信提交或义务快照。 unbound 不能作为 Stop 放行依据；读取或本地分支恢复后，重新 escalate open，原记录保留。 旧记录没有 HEAD 时同样不凭时间推测放行。

Stop 遇到分支状态或义务读取异常时，按分支隔离，并在账本记录带脱敏诊断的 stop.error，继续检查其他任务。 上报留档或异常提示都不代表已交付，不豁免验证、独立评审、人工确认和其他门禁。

常见的合并拒绝原因：

提示处理
bad_commit_message分支上有提交不符合提交信息规范；harness status 会列出具体提交与条目，在任务分支改写后再重新 verify、review
review_missing / review_blocked运行 harness review；被拒时按发现修复，提交后重新 verify、review
gate_change_unconfirmedAgent 展示确认摘要；由人在自己的终端执行它给出的带 --yes 的确认命令，再告诉 Agent 继续
plan_unapproved大改动没有实施授权记录；补齐方案，你同意后由 Agent 照录原话运行 harness approve
conflict在任务分支上 git merge main 解决冲突，再重新验证与评审
main_moved合并或同步过程中主分支前进了，重新运行同一条命令，已有证据会复用
delivery_remote、delivery_local交付方式和当前命令不匹配：远程模式下用 harness submit，本地模式下用 harness merge
base_stale、not_fast_forward本地主分支与远程不一致：先 harness sync；本地有远程没有的提交时 sync 拒绝，不改写历史
platform_missing、platform_failed平台命令没装或调用失败，由人安装并运行 gh auth login 或 glab auth login
review_stale主分支在评审之后改了本分支也改过的文件；在任务分支上 git merge main 并提交，再重新验证与评审
验证结果 incomplete先看每项 reasonCode 与 blockedBy，补齐依赖或修正必验路径映射后重跑受影响检查
主 Worktree 不在 main 或不洁净Agent 先核对状态并保留已有改动，按项目规则准备主 Worktree；需要处置用户改动时先说明具体对象并取得授权
