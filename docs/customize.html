配置与维护

按项目定制

按项目实际情况调整配置、验证检查和拦截规则。

本页内容
本页内容
  1. config.json
  2. verify.json
  3. policy.json
  4. golden/tasks.json

可以直接对 Agent 说“请检查当前规则和检查配置，按项目实际情况提出调整方案，说明影响并按授权实施”。配置改动仍按门禁流程验证、评审和人工确认。

四个文件决定门禁的行为，Agent 可以直接改，但它们都属于门禁改动，合并前要人确认，合入后才生效。

config.json

主分支名、合并要求、提交格式、评审后端、验收清单模式、任务分级阈值、Worktree 清理命令。

verify.json

改了哪些路径跑哪些检查、检查的级别、执行目录与依赖，以及先红后绿与改动行覆盖率的复算配置。

policy.json

启用哪些预设、关掉哪些规则、项目自己的拦截规则。

golden/tasks.json

对规则本身的回归用例，改坏规则的分支在 verify 阶段就被拦下。

加一条项目规则，例如禁止改已上线的迁移基线：

policy.json 片段
{
  "id": "migration-baseline",
  "kind": "write-protect",
  "paths": ["db/migrations/0001_*.sql"],
  "reason": "迁移基线已经上线，改它会让已部署的库与代码不一致",
  "fix": "新增一个迁移文件，不要改已有的基线"
}

每条规则都要写 reason 和 fix，拦截时原样展示给 Agent。默认启用的预设：

预设内容
secrets禁止读取、写入或用命令外发私钥、凭据与证据密钥；.env 这类开发环境的环境文件不拦
git-safety拦截递归删除、丢弃改动、强删 Worktree、删分支、强推、stash、--no-verify，以及在主分支上合并、变基、重置
gate-self保护执行器入口与绕过开关；轮换密钥与人工确认只能由人执行
plan-first没有实施授权时只能写方案文件，大改动合并前必须有授权记录
main-worktree（可选）主 Worktree 只用来合并，多个会话并行时推荐启用

字段的完整说明见参考手册的配置一节。
